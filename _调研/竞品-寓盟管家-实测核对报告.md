## 2. ⭐ 最重要的结论：**竞品完全没有保障房（公租房）业务**

### 2.1 验证过程

我逐项核对了菜单全文与关键业务页，**未发现任何一项**与保障房相关：

| 保障房必备环节 | 竞品是否存在 |
|---|---|
| 资格审核（收入/住房/户籍核查） | ❌ **无** |
| 轮候库 / 轮候排序 / 打分 | ❌ **无** |
| 摇号 / 公证 / 中签名单 | ❌ **无** |
| 配租 / 选房 | ❌ **无** |
| **租金补贴 / 发放** | ❌ **无** |
| 准入退出复核 | ❌ **无** |
| 多部门联审（民政/公安/不动产） | ❌ **无** |
| 监管报送 / 住建备案 | ⚠️ 有"备案"菜单，但为**企业内部备案**（房源/合同/流水备案），非政府监管报送 |
| 保障房类型区分（公租房/保租房/人才公寓） | ⚠️ 房源字段有"业务状态""项目类型"，但**无保障房属性** |

### 2.2 关键证据：「住房申请」页实测

这是竞品**最接近**保障房的一环，我实测了它的表头与状态：

| 项 | 实测内容 |
|---|---|
| **路由** | `#/contract/leaseApply` |
| **页面标题** | 住房申请 |
| **表格列** | 序号 / 状态 / 申请人信息 / 小区·项目名称 / 房源编号 / 房源信息 / 房号地址 / 申请备注 / 申请时间 / 操作 |
| **状态枚举** | **全部 0 / 待处理 0 / 待入住 0 / 已入住 0 / 已驳回 0 / 无效 0** |
| **数据** | 共 0 条（演示数据未含） |

**判定**：这是**「租房申请 → 入住」的简单流转**，本质是租赁意向单。
**它没有**：资格条件、审核要素、轮候、摇号、补贴、退出复核、监管报送。

> **结论：竞品的"住房申请"与漳州标要求的"保障房全业务闭环"不是同一层次的需求。**
> 这意味着**我们的方案在保障房领域没有直接竞品**——这既是机会，也说明**这块没有可抄的成熟做法，必须靠业务确认（对应第一轮 §10-2 的 C8 风险）**。

## 3. 实测功能细节（可用于校准我方设计）

### 3.1 空间树结构（实测）

房源页实测的空间层级：

```
库房（xx库房，芜湖市-繁昌县）
  └ 主仓
      └ 1栋
          └ 1单元
              └ 1层
                  └ 101 / 102 / 103 / 104 …（房间卡片）
```

**对比我方设计**：我方 `bp_asset_space` 为 `小区 → 楼栋 → 单元 → 楼层 → 房间 → 床位` 6 级。
竞品实测为 `库房 → 主仓 → 栋 → 单元 → 层 → 房间`，**多了一层"库房/主仓"**（相当于"园区/仓库"概念）。

> **校准建议**：我方空间树**层级足够**（6 级已能覆盖），但应确认**是否需要"园区/多项目"层级**——
> 竞品用"库房→主仓"承载了"一个客户管多个物理点"的场景。我方目前用 `org_id`（组织）承载，需确认是否够。

### 3.2 房源卡片字段（实测）

每个房间卡片显示：

| 字段 | 示例 |
|---|---|
| 房号 | `101` |
| 朝向 / 面积 / 类型 | `南-100㎡` / `库房` |
| 租金 | `¥60000元/月` |
| 租客 / 付款方式 | `杨雪 / 押1付3` |
| 合同期 | `2027.10.01~2028.09.30` |
| 状态 | `已租` / `已租待签字` / `空置` |
| 空置天数 | `空 2 天` |
| 欠款天数 | `欠款3天` |
| 操作图标 | 签 / 欠 / 锁等 |

**对比我方**：我方 `bp_asset_house` 有 `house_status`、`rent_standard`、`area`、`orientation`、`floor_no` 等，
**但没有**「**空置天数**」「**欠款天数**」这类**派生指标字段**。

> **校准建议（可采纳）**：房源列表卡片显示"空置 N 天""欠款 N 天"是**运营视角的关键信息**。
> 我方应在 `bp_rpt_metric_daily`（报表预聚合）或房源查询的**计算列**中提供这两个派生值，
> **不必落成实体列**（避免维护成本），但**界面必须有**。

### 3.3 财务实测（信息量大）

| 项 | 实测内容 |
|---|---|
| 二级标签 | 账单 / 流水 / 付款 / 发票 / 收据 / 报销 / 转账通知 / 税率配置 |
| 视图 | 汇总 / 明细 |
| **账单摘要示例** | `房屋租金/滞纳金`、`房屋租金/水费`、`房屋租金/服务费/滞纳金`、`水费` |
| 状态枚举 | 待收/待付 16065【待收 10669 待付 5396】/ 待平账 339 / 付款中 207 / 已结算 / 作废 / 坏账 17 |
| 快捷筛选 | 逾期 9251 / 今日 11 / 近 7 天 33 / 游离账单 |
| 财务指标 | 应收 30664.88 / 已收 593608.33 / 已付 169180.06 / 待收 2499358148.90 |
| **催收** | 有 `已催收` 标记（**存在催收功能**） |
| 分页 | 共 **10000 条** |

**关键发现**：

1. **账单摘要用「科目组合」**（如 `房屋租金/滞纳金/服务费`）——**一条账单可含多个费用项**。
   我方 `bp_fin_bill` 需确认是否支持**多费用项合并一张账单**（我方的 `bp_fin_bill` + 明细结构应支持，需核对）。
2. **有"坏账"状态**（17 条）——我方设计中**未明确"坏账核销"流程**。
3. **有"待平账"概念**（339 条）——这对应"**未知款项/待认领**"，我方有 `unknown_flag`，语义接近。
4. **有"游离账单"筛选** —— 含义待确认，可能是"无关联合同的账单"。
5. **有"催收"功能** —— 我方 `bp_fin_dunning_record`（催缴记录）已设计，**方向一致**。
6. **有"报销""发票""收据""转账通知""税率配置"** —— 我方账务域侧重**收租**，
    ⚠️ **未包含"报销""税率配置"**，需确认是否纳入（政府客户可能需要）。

### 4.3 结论：竞品校准后的定位

```
┌──────────────────────────────────────────────────────────┐
│  竞品「寓盟管家」= 市场化公寓租赁 SaaS                     │
│    强项：房源/合同/财务/营销/业绩/多经/日租/供应商          │
│    弱项：无保障房、无轮候摇号、无补贴、无监管报送           │
├──────────────────────────────────────────────────────────┤
│  我方「业务平台」= 政务保障房内核 + 多场景扩展              │
│    强项：资格审核/轮候/摇号/配租/补贴/退出/监管 + IoT 深度  │
│    待补：知识库、物资库房、供应商结算、调价管理、坏账核销    │
└──────────────────────────────────────────────────────────┘
```

**战略判断**：
1. **保障房领域竞品无法对标** → 我们的方案**必须靠业务确认**，不能抄竞品（**强化了 C8 风险**）；
2. **市场化公寓场景**（公寓/宿舍/酒店民宿/出租房）**竞品功能更完整** → 我方二期做这些场景时，**竞品是重要参考**；
3. **共有能力**（大屏/巡房/审批/工单/备案/停车）→ 我方**必须做到不弱于竞品**，否则在演示环节吃亏。

## 7. 结论摘要

| # | 结论 |
|---|---|
| 1 | **竞品是市场化公寓租赁 SaaS（PMS），完全不含保障房业务** —— 我方在保障房领域无直接竞品 |
| 2 | 竞品的"住房申请"仅是**申请→入住简单流转**（5 个状态），无资格审核/轮候/摇号/补贴 |
| 3 | 竞品完整菜单 = **一级 6 + 二级 16 组 + 三级约 70 项**，重心在**房源/合同/财务/营销/业绩/多经/日租/供应商** |
| 4 | 竞品**也有**大屏（2 个）、巡房、审批流、工单、备案、停车、开放平台 —— **这些我方必须做到不弱** |
| 5 | 我方**建议新增**：知识库、物资库房、供应商结算、调价管理、坏账核销、空置/欠款天数派生指标 |
| 6 | 我方**不建议**照搬：营销/优惠券/业绩提成/宽带/增值服务（保障房无此需求） |
| 7 | **最重要**：保障房业务**无竞品可参考** → **必须靠业务方确认流程**（强化 C8 风险，建议尽早召开业务确认会） |
