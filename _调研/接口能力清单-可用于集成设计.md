## 3. 关键设计结论

### 3.1 结论一：IoT 平台**已原生支持"以人为中心"的门禁授权** ★

`8.2.1 人员授权`（`/ymd/restful/auth/action`）的入参形态是：

- 一个人员（`userAccountObj`，可多个人）
- 对多把锁（`lockId` 逗号分隔）
- 一个时间区间（`startDate`/`endDate`）

**这意味着**：门锁产品方案中宣传的「选人即授权、系统自动匹配钥匙、批量下发」，其**设备侧能力在 IoT 平台已经具备**。

→ **业务平台不需要重造授权下发引擎**，只需负责：
1. 决定"谁、在什么空间、拥有什么权限层级、什么有效期"（**业务规则层**）
2. 把结果翻译成 IoT 平台的人员授权调用（**翻译/编排层**）
3. 跟踪授权任务结果（`/ymd/restful/syncTask/result/list`）并处理失败重试（**可靠性层**）
4. 记录审计与合规证据（**留痕层**）

### 3.2 结论二：存在**新旧两套并存的授权接口**，必须做选型收敛

| 维度 | 旧接口（§7 `lockPt-service/pt/*`） | 新接口（§8 `restful/*`） |
|---|---|---|
| 授权主体 | **锁**（`lockId` 单一） | **人**（`userAccountObj`，可多个） |
| 批量能力 | ❌ 只能逐锁、逐介质调用 | ✅ 多锁 × 多人一次调用 |
| 介质覆盖 | 身份证/卡、指纹、期限码、访客码、APP | 统一 `channelType` + 通用介质（含人脸） |
| 人脸 | 仅 §7.7.1 通用介质授权 | ✅ 纳入统一介质体系 |
| 结果查询 | 同步返回 | ✅ 异步任务 + `syncTask/result/list` 轮询 |

**建议设计原则**：
- **主链路统一走 §8 人员维度接口**（人-锁-时间三元组，契合"以人为中心"与四级权限模型）；
- **§7 旧接口仅作为补充通道**，用于人员维度接口覆盖不到的能力：**期限码 / 访客码（`setExpirePwd` / `setVisitorPwd`）**、**清空整锁授权（`clearLockAuth`）**、**指纹直传（含公安身份证指纹模板 `complementedFlg=1/2`）**；
- 在业务平台侧建立**统一授权编排服务**，屏蔽两套接口差异，对上层只暴露「按人授权 / 按规则批量授权 / 按介质授权」三种语义。

### 3.3 结论三：实名认证链路已经打通，可直接复用

业务平台**无需自建公安部对接**：
- 个人实名：§9.1 `serviceV2`（三要素 + 人照比对）
- 组织实名：§9.2 `orgVerify/*`
- 人脸比对（1:1）：§9.3 `commandId=E755B3AB842F4A11221985D5D01D32E`

→ 业务平台的「实名认证」模块应设计为**调用方 + 结果留痕方**，而非能力实现方。身份证加密区读取、指纹模板下发亦由设备侧/IoT 平台承担（`cardType=1`、`checkSelf`、`complementedFlg`）。

### 3.4 结论四：回调能力**非常有限**，业务平台必须有主动补偿机制 ★

文档中**唯一**的平台→业务系统推送是 **§6.6 开门记录回调**（`/callback/bite`），且：
- 回调地址**必须联系开发人员配置**，无自助配置接口；
- 只推**开门记录**（`openType`/`lockId`/`targetUserMobile`/`openTime`）。

**文档中未提供回调/推送的能力（业务平台必须自行解决）**：

| 缺失的推送能力 | 影响 | 业务平台的应对设计 |
|---|---|---|
| 授权结果回调 | 无法实时知道授权是否下发到锁 | 授权后轮询 `syncTask/result/list` + 定时对账 |
| 设备在线/离线状态变更 | 无法实时感知锁离线 | 定时全量/增量拉取 + 门锁在线率计算 |
| 电量/欠压告警 | 无法及时通知换电池 | 定时拉取电量 + 阈值判断 + 业务侧告警 |
| 防拆/试错/挟持告警 | 安全事件滞后 | 从开门记录 `openType`（1023 劫持码/1034 挟持指纹）反推 + 定时拉取 |
| 网关状态 | 无法感知网关掉线 | 定时拉取 |

→ **架构结论**：业务平台的设备域必须设计为**"回调优先 + 定时对账兜底"双通道**，且对账任务要能承受设备量级（漳州项目 5,771 套）并具备幂等性。

### 3.5 结论五：业务平台必须自建的能力清单

以下能力在 IoT 接口文档中**完全不存在**，是业务平台的核心自建范围：

| 能力域 | 文档中 | 说明 |
|---|---|---|
| **空间层级管理** | ❌ 无 | 仅有 `organId` 平坦字段，**无空间树 CRUD、无层级继承** |
| **房源/房间台账** | ❌ 无 | 无房源状态、面积、户型、空置率 |
| **保障对象档案与资格审核** | ❌ 无 | 无申请、审核、轮候、摇号、选房、退出 |

| **租金与账单** | ❌ 无 | 无账单、应收应付、滞纳金 |
| **补贴发放** | ❌ 无 | 无 |
| **欠费与权限关停联动** | ❌ 无 | 无（这是业务平台的编排能力） |
| **设备在线状态/心跳查询** | ❌ 无 | 文档 6.2「获取门锁信息」是否含在线状态**未明确**，需实测确认 |

## 5. 对业务平台集成层的设计含义（摘要）

```
业务平台
  │
  ├── 集成层（Adapter / Anti-Corruption Layer）★自建
  │     ├── YmdIotClient          统一 HTTP 客户端：token 缓存(30min)、AES、MD5 sign
  │     ├── 接口路由与降级         人员维度优先，旧接口兜底
  │     ├── 幂等与重试             授权/删除操作幂等键
  │     ├── 授权编排服务           业务规则 → 人员授权调用
  │     └── 对账补偿任务           定时拉取 + 状态校准
  │
  └── 通道
        ├── API（主动调用）    token + AES + sign
        └── Callback（被动接收）开门记录 /callback/bite
```

**核心原则**：
1. **Token 必须集中缓存**（30 分钟有效），避免每次调用都换取 token 造成额外开销与限流风险。
2. **AES 密钥依赖 token 前 25 位** → token 刷新与加密过程强耦合，必须放在同一组件内保证一致性。
3. **所有授权动作必须产生本地任务记录**，与 `syncTask/result/list` 结果对账，不可"发出去就算成功"。
4. **开门记录回调必须幂等落库**（以 `eventId` 去重），并同时保留定时拉取通道作为兜底。
5. **绝不在业务平台直连 EMQ/MQTT 处理设备授权**，设备链路维持现状（EMQ），业务平台只经 API。
