## 0. 重要：本次压测的能力边界（先讲清限制，避免误读）

| 限制 | 说明 | 对结论的影响 |
|---|---|---|
| **`innodb_buffer_pool_size` 仅 128 MB** | 生产建议 16–32 GB | **绝对耗时不具代表性**，只用于判断"是否走对索引/分区" |
| **`sync_binlog=1` + `innodb_flush_log_at_trx_commit=1`** | 每次提交都 fsync；且账号**无 SUPER 权限**无法临时关 binlog | 灌数吞吐被压到 ~1,000 行/秒；**生产应关闭 binlog 或用 `LOAD DATA`** |
| **本测试库仅 1 个租户**（`tenant_id` 基数=1） | 所有索引的租户前缀**无选择性** | 优化器代价估算失真，**索引选择结论需在生产多租户下复评** |
| 灌数规模 16 万（原计划 30 万） | 灌至 16 万时**连接被服务器断开**（`Lost connection during query`），判定为测试环境资源耗尽 | **16 万已足够验证分区裁剪与索引命中**；卡方 Index 构建在 16 万行上仅 14 s |
| 未跑并发压测 | 未验证高并发下的锁竞争与连接池 | 并发能力待生产环境或专门压测环境验证 |

## 1. ⭐ 核心结论一：分区裁剪**完全符合设计预期**

这是本次压测**最重要的验证项**——17.5 亿条记录规模下，分区裁剪是查询性能的基础。

| 测试 | 查询条件 | **EXPLAIN 实际命中分区** | 索引 | 耗时 |
|---|---|---|---|---|
| T1-a | 单日（2026-11-05） | **`p202611`（仅 1 个）** ✅ | `idx_tenant_time` | 0.005 s |
| T1-b | 单月（2026-10） | **`p202610`（仅 1 个）** ✅ | `idx_tenant_person_time` | 0.142 s |
| T1-c | 跨 3 月（10~12） | **`p202610,p202611,p202612`（3 个）** ✅ | — | 0.476 s |
| T1-d | **无时间条件**（对照组） | **全部 7 个分区** ✅ | — | 0.113 s |

**验证价值**：
- 有 `open_time` 范围条件时，MySQL **只扫必要分区**（T1-a 仅 1 个分区）；
- 无时间条件时**扫全部 7 个分区**——证明裁剪确实由 `open_time` 驱动，不是"碰巧只扫了一个"。

**分区数据分布实测**（写入端也正确）：

| **`pmax`** | **0** | ✅ **兜底分区零数据 —— 说明分区边界正确** |

## 2. ⭐ 核心结论二：索引设计**有效命中**（含"Using index"覆盖索引）

| 测试 | 期望索引 | **实际使用** | 类型 | 耗时 |
|---|---|---|---|---|
| 按人+时间 | `idx_tenant_person_time` | ✅ 命中 | range | 0.004 s |
| 按房源+时间 | `idx_tenant_house_time` | ✅ 命中 | range | 0.003 s |
| 按设备+时间 | `idx_tenant_device_time` | ✅ 命中 | range | 0.004 s |
| 按开门方式+时间 | `idx_tenant_opentype_time` | ✅ 命中 | range | 0.022 s |
| **幂等查询**（回调去重） | `uk_tenant_event` | ✅ 命中 | **const** | 0.003 s |
| 大屏按组织聚合 | `idx_tenant_org_status` | ✅ 命中 | ref + **Using index** | 0.006 s |
| 多维房源筛选 | — | ✅ 命中 | ref | 0.017 s |

**关键观察**：多条查询出现 **`Using index`（覆盖索引）**，即**无需回表**——说明索引列选择合理，避免了大表随机 IO。

**幂等查询 `type=const`**：这是最优的访问类型（常量查找），证明回调去重路径 `(tenant_id, event_id, open_time)` 的索引设计正确，**重复推送可被极快地识别**（对应第二轮 §4.5 的可靠性设计）。

## 3. 业务算法 SQL 验证（漳州标关键指标）

### 3.1 【指标 20】不可信开门方式占比 > 20%

```sql
SELECT house_id, COUNT(*) total_cnt,
       SUM(CASE WHEN is_trusted=0 THEN 1 ELSE 0 END) untrusted_cnt,
       ROUND(SUM(CASE WHEN is_trusted=0 THEN 1 ELSE 0 END)/COUNT(*)*100,2) untrusted_pct
FROM bp_dev_access_record
WHERE tenant_id=? AND open_time>=? AND open_time<?
GROUP BY house_id HAVING untrusted_pct>20 ORDER BY untrusted_pct DESC;
```

| 项 | 结果 |
|---|---|
| 执行计划 | `key=idx_tenant_house_time`，**`partitions=p202610,p202611,p202612`（裁剪到 3 个）** |
| ⚠️ Extra | `Using index condition; **Using temporary; Using filesort**` |
| 耗时 | **0.801 s**（16 万行 / 覆盖 5,771 房源） |
| 结论 | ✅ **可行**；`Using temporary + filesort` 是 `GROUP BY + HAVING` 的固有开销，在更大数据量下会线性增长 |

> **优化建议**：该统计属于**周期性批处理**（非实时），建议
> ① 由**定时任务预聚合**到 `bp_rpt_metric_*`（对应第二轮 §7.3 设计）；
> ② 大屏只读预聚合结果，**不在线跑此聚合**。

### 3.2 【指标 19】长期未开门（自动巡查）

| 项 | 结果 |
|---|---|
| 执行计划 | `h` 走 `uk_tenant_housecode`；`r` 走 `idx_tenant_house_time` + `Using index` |
| 耗时 | **0.227 s**（3,536 套 OCCUPIED 房源，LEFT JOIN 160 万级记录） |
| 结论 | ✅ **可行**，JOIN 走了正确的索引 |

### 3.3 工单闭环时效（考核"2 小时一票否决"）

| 测试 | 耗时 | 结果 |
|---|---|---|
| SLA 超时统计（按类型） | 0.033 s | ✅ |

## 4. ⚠️ 发现的优化点：时间排序查询需显式指定索引

### 4.1 现象

同一查询，仅改变排序字段/是否指定索引，性能差异显著（3 轮取中位）：

| 写法 | 优化器选择的索引 | Extra | **中位耗时** |
|---|---|---|---|
| 自然 `ORDER BY open_time DESC` | `uk_tenant_event` | `Using index condition; **Using filesort**` | **0.627 s** |
| 自然 **无排序** | `uk_tenant_event` | `Using index condition` | **0.107 s** |
| **`FORCE INDEX(idx_tenant_time)`** + `ORDER BY open_time DESC` | `idx_tenant_time` | `Using index condition; **Backward index scan**` | **0.168 s** |
| 小结果集（按房源） | `idx_tenant_house_time` | `Backward index scan; Using index` | **0.015 s** |

### 4.2 根因分析

**排序是主要开销**（0.627 s vs 0.107 s，差 5.9 倍）。

索引结构决定了是否能免排序：

| 索引 | 列顺序 | 对「按租户过滤 + 按时间排序」是否有序 |
|---|---|---|
| `idx_tenant_time` | `(tenant_id, open_time)` | ✅ **完全匹配** → 可反向索引扫描，**免排序** |
| `idx_tenant_house_time` | `(tenant_id, house_id, open_time)` | ❌ `open_time` 在第三位，跨 `house_id` 时**无序** → 必须 filesort |
| `uk_tenant_event` | `(tenant_id, event_id, open_time)` | ❌ 同上 → 必须 filesort |

优化器**选择了 `uk_tenant_event`**（或 `idx_tenant_person_time`），导致对 56,804 行的区间结果做 filesort；
而 `idx_tenant_time` 本可免排序。**`FORCE INDEX` 后耗时从 0.627 s 降到 0.168 s（快 3.7 倍）**。

### 4.3 为什么优化器会选错？

**本测试库只有 1 个租户** → `tenant_id` 基数=1 → 所有索引的租户前缀**毫无选择性**，
优化器无法区分 `idx_tenant_time` 与 `uk_tenant_event` 的价值，代价估算失真。

> **生产多租户下应重新评估**。但**不能依赖优化器自动选对**——因为它对"排序友好性"的评估本就保守。

### 4.4 建议动作（写入开发规范）

| # | 建议 | 说明 |
|---|---|---|
| 1 | **凡"按租户 + 时间范围 + 按时间排序"的查询，显式提示 `idx_tenant_time`** | 报表、导出、通行记录列表均属此类 |
| 2 | 或改用**游标分页**（`WHERE open_time < :lastOpenTime ORDER BY open_time DESC LIMIT n`） | 天然走 `idx_tenant_time`，且避免深分页 |
| 3 | **禁止对 `bp_dev_access_record` 使用 `ORDER BY id`** | `id` 与 `open_time` 不同序，必然 filesort |
| 4 | 深分页统一走游标（见 §5） | |

### 4.5 诚实说明：一个未能复现的现象

首次测试（`_perf_test2.py`）中 `ORDER BY id DESC` 曾出现 **28.165 s**，
但**后续 3 轮复测无法复现**（均为 0.559 s 左右）。

**判定**：该 28 s 为**一次性异常**（可能受此前灌数残留 IO、优化器统计未刷新、或并发干扰影响），
**不作为稳定结论**。上文 §4.1 的 0.627 s / 0.107 s / 0.168 s 是 3 轮中位数，**可信**。

| 分页 | 耗时 |

## 6. ⚠️ 一个"看似问题、实为查询写法"的案例（如实记录）

T9 的 JOIN 查询执行计划显示 `bp_asset_space_device` 为 **`type=ALL`（全表扫描）**，
一度疑似"索引缺失"。**深入验证后确认不是索引问题**：

| 对比 | 执行计划 | 耗时 |
|---|---|---|
| 同一索引 `idx_tenant_house`，**单独查绑定表** | `type=ref`, `Using index` | **0.003 s** |
| 同一索引，**放在 JOIN 中** | `type=ALL`, `key=null` | 0.102 s |

**根因**：该 JOIN 中 `bp_asset_space_device` **没有选择性过滤条件**（它只是被 JOIN 以覆盖全部活跃绑定），
优化器遂选择"从 `bd` 全扫 5,737 行 + hash join"。

**结论**：索引 `idx_tenant_house(tenant_id, house_id, is_active)` **存在且可用**，
**不是设计缺陷**。在 5,737 行规模下 0.102 s 可接受。
> 如实记录此案例，是为了说明：**EXPLAIN 出现 `type=ALL` 不等于缺索引**，
> 必须结合"是否有过滤条件"判断，避免误报设计问题。

## 8. 灌数方法的重要教训（对后续开发有直接价值）

### 8.1 PyMySQL 的 `executemany` 是**逐行 INSERT**

首次灌数仅 **97 行/秒**，耗时异常。排查发现 PyMySQL 源码：

```python
# pymysql/cursors.py
def executemany(self, query, args):
    return self._do_execute_many(query, args)
    # 内部为 sum(self.execute(query, arg) for arg in args)  ← 逐行发送！
```

**实测对比**：

| 方法 | 吞吐 | 相对 |
|---|---|---|
| `executemany`（逐行） | **170 行/秒** | 1× |
| 多值 INSERT × 500 | 1,538 行/秒 | 9× |
| **多值 INSERT × 2,000** | **4,343 行/秒** | **26×** |
| **多值 INSERT × 10,000** | **5,610 行/秒** | **33×** |

### 8.2 建议写入开发规范

| # | 规范 | 理由 |
|---|---|---|
| 1 | **批量写库必须用多值 INSERT**（MyBatis 用 `foreach` 拼 `VALUES (..),(..)`） | 逐行 INSERT 慢 30 倍 |
| 2 | 单条 INSERT 建议 **2,000 行/批**（吞吐与 `max_allowed_packet` 的平衡点） | 10,000 行/批略快但报文大 |
| 3 | 大批量导入生产环境应使用 **`LOAD DATA INFILE`**（服务端读文件） | 本测试因 `local_infile=0` 且 `secure_file_priv` 在服务端而无法使用 |
| 4 | 大批量导入前**临时移除非必需唯一索引**，导入后重建 | 本测试索引重建仅 14 s（16 万行），收益明显 |
| 5 | **批量导入应关闭 `binlog`**（或使用 `LOAD DATA`），生产需 DBA 配合 | 本测试 `sync_binlog=1` 导致吞吐被压到 1,000 行/秒 |
