# 智慧物业 V1 多场景扩展设计建议

> 场景：住宅物业、酒店/民宿、网约房、出租房、公寓、办公楼、宿舍、校园  
> 结论：需要做一次架构级优化，但不是把酒店/校园全部塞进物业 V1  
> 核心：从“物业系统”升级为“多场景空间资产运营平台”，物业只是其中一个场景包

---

## 1. 当前设计能支撑到哪里

当前设计已经具备：

```text
多租户
组织/项目
五级地址
空间结构模板
资产类型
空间/房屋
人员主档
合同
计费方案
账单/收款/收据/发票
设备资产
授权/钥匙包
工作流
服务工单
报表
```

这些可以支撑：

```text
住宅物业
商业物业
办公楼租赁
公寓租赁
宿舍管理
部分校园场景
```

但不能直接支撑：

```text
酒店/民宿的房态日历
预订/入住/退房
OTA/渠道订单
短租动态价格
客房保洁
owner 分成结算
网约房的入住登记/监管
校园的学生/教职工/宿舍分配
```

原因是当前模型默认：

```text
一个项目一种物业类型
一个项目一个空间模板
长期合同为主
周期账单为主
业主/住户关系为主
```

多场景下需要升级。

## 2. 需要新增的核心模型

### 2.1 场景包 Scene Profile

平台不能用一个菜单覆盖所有场景，需要场景包：

```text
PROPERTY_RESIDENTIAL    住宅物业
PROPERTY_OFFICE         办公楼物业
RENTAL_APARTMENT        公寓租赁
RENTAL_HOUSE            出租房
DORMITORY               宿舍
HOTEL                   酒店
BNB                     民宿
ONLINE_RENTAL           网约房
CAMPUS                  校园
MIXED_USE               混合业态
```

场景包决定：

```text
菜单
角色模板
空间模板
资产类型
合同/订单类型
计费策略
报表
```

### 2.2 经营模式 Business Mode

一个项目可以是混合业态：

```text
一栋楼住宅
一层商业
一栋公寓
一栋酒店
一个园区
```

所以不能只在租户/项目上定一个场景。

建议：

```text
tenant.scene_profile       租户主场景
project.business_mode      项目默认模式
building.business_mode     楼栋模式
space/unit.business_mode   最小资产模式
```

继承：

```text
资产自身 > 楼栋 > 项目 > 租户
```

这样支持：

```text
住宅 + 商业 + 公寓 + 酒店混合
```

### 2.3 空间模板多模板

当前设计是“项目选择一个空间模板”。

多场景下应改为：

```text
项目默认模板
楼栋/区域可覆盖模板
```

示例：

```text
住宅楼：期/苑/幢/单元/楼层/房号
商业裙楼：楼/楼层/商铺
酒店楼：楼/楼层/房型/房间
公寓楼：楼/楼层/房间/床位
宿舍楼：楼/楼层/房间/床位
办公楼：楼/楼层/单元
校园：校区/建筑/楼层/房间
```

数据：

```text
bp_iam_org.space_template_id       项目默认
bp_asset_space.space_template_id   楼栋覆盖
```

### 2.4 资产类型多场景

资产类型继续平台级：

```text
bp_asset_type
  scene_code
  type_code
  type_name
  type_category
```

示例：

```text
住宅：高层、多层、排屋、商业
公寓：整租、合租、床位
酒店：标准间、大床房、套房
宿舍：4人间、6人间、8人间
办公：独立办公室、工位、整层
校园：教室、实验室、宿舍、场馆
```

### 2.5 人员关系多场景

人员主档平台共用，但关系按场景扩展：

```text
物业：业主、家人、承租人、同住人
公寓：租客、同住人
酒店/民宿：住客、访客
宿舍：学生、教职工、宿管
校园：学生、教师、职工、访客
办公：租户员工、访客
```

不要把酒店住客、学生塞进 `prop_owner_unit`。

建议：

```text
bp_person                 人员主档
bp_person_relation        通用关系框架
prop_owner_unit           物业业主关系（保留）
lodging_stay              住宿入住关系
campus_student            校园学生关系
```

### 2.6 合同与订单分离

长期租赁和短租订单不是一回事：

```text
合同 Contract
  物业服务合同
  商铺/办公租赁合同
  公寓租赁合同
  场地合同

订单/预订 Order/Booking
  酒店预订
  民宿预订
  网约房订单
  会议室预订
  校园场馆预订
```

建议：

```text
bp_contract        合同生命周期
bp_booking         预订
bp_stay            入住/在住
bp_order           订单/消费
```

不要用合同表硬套酒店订单。

### 2.7 库存与房态日历

酒店/民宿/网约房需要：

```text
房型库存
日期库存
可售/不可售
价格日历
预订占用
超售控制
保洁状态
维修房
```

建议新增：

```text
bp_inventory_calendar
  inventory_id
  biz_date
  total_count
  available_count
  sold_count
  price
  status
```

```text
bp_room_status
  room_id
  clean_status
  inspect_status
  maintenance_status
  current_stay_id
```

这是酒店/民宿/网约房的核心，不应塞进物业账单。

### 2.8 入住与在住

```text
预订
→ 入住
→ 在住
→ 退房
→ 保洁
→ 结算
```

建议：

```text
bp_booking
bp_stay
bp_checkin_record
bp_checkout_record
```

字段：

```text
住客
房间
入住时间
退房时间
入住人数
证件
押金
房费
渠道
订单号
```

### 2.9 渠道与 OTA

酒店/民宿/网约房需要：

```text
携程
美团
飞猪
Airbnb
小猪
自如
抖音
小红书
直订
```

建议：

```text
bp_channel_account
bp_channel_booking
bp_channel_sync_log
```

本期不建议实现全部渠道，只留接口。

### 2.10 客房保洁

```text
待清洁
清洁中
待查房
已清洁
维修房
```

建议：

```text
bp_housekeeping_task
  room_id
  task_type
  status
  assignee
  start_time
  finish_time
```

### 2.11 收入结算

酒店/民宿/网约房涉及：

```text
房费
渠道佣金
owner 分成
物业费
能耗费
押金
退款
```

建议：

```text
bp_settlement
bp_settlement_item
```

不要把 owner 分成塞进物业利润表。

### 2.12 校园扩展

校园需要：

```text
校区
院系/部门
学生/教职工
宿舍分配
门禁
水电
报修
场馆
```

建议：

```text
campus_org
campus_student
campus_staff
campus_dorm_alloc
campus_venue_booking
```

空间模板：

```text
校区/建筑/楼层/房间
```

### 2.13 办公楼扩展

办公楼需要：

```text
楼宇
楼层
单元
租户
租赁合同
物业费
门禁
会议室
访客
```

大部分可复用物业合同/计费/设备授权，增加：

```text
office_unit
office_tenant
office_meeting_room
```

## 3. 哪些升级为平台能力

| 能力 | 平台化 | 说明 |
|---|---|---|
| 场景包/经营模式 | 是 | 租户/项目/楼栋/资产 |
| 空间模板 | 是 | 多模板、楼栋覆盖 |
| 资产类型 | 是 | 按场景 |
| 人员主档 | 是 | 共用 |
| 人员关系框架 | 是 | 场景扩展 |
| 合同生命周期 | 是 | 合同通用 |
| 预订/入住 | 是，平台业务能力 | 酒店/民宿/场馆共用 |
| 库存日历 | 是，平台业务能力 | 房型/场地/会议室 |
| 账单/收款/发票 | 是 | 通用计费 |
| 设备资产 | 是 | 设备作为资产 |
| 设备授权/钥匙包 | 是 | 短租有效期 |
| 工作流 | 是 | 多场景审批 |
| 消息/文件/字典 | 是 | 共用 |
| 报表框架 | 是 | 场景指标扩展 |

## 4. 哪些保留为场景能力

```text
住宅物业费
能耗费公摊
业主委员会
物业服务合同
酒店动态价格
OTA 渠道
民宿 owner 分成
网约房监管登记
校园学生/宿舍分配

```

这些不能强行平台化。

## 7. 当前设计需要调整的地方

### 7.1 项目只能选一个空间模板

改为：

```text
项目默认模板
楼栋可覆盖模板
```

### 7.2 项目只有一种业务类型

改为：

```text
project.business_mode
building.business_mode
unit.business_mode
```

### 7.3 合同表承担所有业务

改为：

```text
合同：长期租赁/物业服务
预订/入住：酒店/民宿/网约房
订单：消费/渠道
```

### 7.4 物业账单承担所有收入

改为：

```text
计费内核：账单/收款/发票
场景：物业费、租金、房费、渠道佣金、owner 分成
```

### 7.5 物业人员关系承担所有人员

改为：

```text
人员主档
通用关系
物业业主关系
住宿住客关系
校园学生关系
```

### 7.6 物业菜单写死

改为：

```text
场景包 + 菜单模块 + 角色模板 + 功能开关
```

## 8. 实施建议

### 不要现在做

```text
酒店 OTA 全部渠道
网约房监管上报
民宿 owner 分成
校园完整教务
```

这些是独立产品线，不要在物业 V1 一次做完。

### 现在应该做

```text
场景包 scene_profile
经营模式 business_mode
多空间模板
资产类型 scene_code
合同/订单/住宿分离
库存日历基础模型
人员关系框架
菜单组合/角色模板
```

这些是底层模型，越早定越省返工。

### 分阶段

```text
Phase 0
  场景包、经营模式、多模板、资产类型、人员关系

Phase 1
  住宅物业 V1

Phase 2
  公寓/出租房/宿舍

Phase 3
  办公楼

Phase 4
  酒店/民宿/网约房

Phase 5
  校园
```

---

## 9. 结论

```text
需要进一步优化设计
但不是把酒店/校园塞进物业 V1
而是把物业系统升级为多场景空间资产运营平台
```

核心调整：

```text
1. 场景包/经营模式
2. 项目默认模板 + 楼栋覆盖模板
3. 合同/订单/住宿分离
4. 库存日历/入住/保洁
5. 人员关系按场景扩展
6. 菜单/角色按场景组合
```

物业 V1 仍然是第一阶段，但底层模型要预留多场景能力，否则后面会被迫重构。
