# 智慧物业 V1 设备授权与人员钥匙包平台能力建议

> 范围：只做业务系统的“人员—空间/设备”授权和人员钥匙包视图  
> 不做：具体钥匙/卡片/人脸/指纹/密码下发，不做设备控制  
> 结论：设备授权和人员钥匙包可以升级为平台能力；具体凭证授权仍归 IOT 平台

---

## 1. 先分清三个概念

### 1.1 业务授权

回答：

```text
谁
在什么时间范围内
可以进入/使用哪个空间或设备
依据是什么
由谁审批
是否有效
```

这是业务规则，适合平台化。

### 1.2 人员钥匙包

回答：

```text
某个人当前拥有哪些空间/设备授权
有效期
来源
状态
```

它是业务授权的聚合视图，适合平台化。

### 1.3 具体钥匙授权

回答：

```text
发哪张卡
写哪个人脸
录哪个指纹
设置什么密码
下发到哪台设备
设备是否执行成功
```

这是 IOT 凭证和下发，不属于业务平台。

---

## 2. 可以升级为平台能力的部分

| 能力 | 是否平台化 | 说明 |
|---|---|---|
| 人员授权 | 可以 | 人员与空间/设备/设备组的授权关系 |
| 设备授权 | 可以 | 授权到设备或设备组，不涉及设备控制 |
| 空间授权 | 可以 | 楼栋/单元/楼层/房间授权，子级继承 |
| 授权有效期 | 可以 | 开始/结束时间、长期、临时 |
| 授权来源 | 可以 | 业主、租户、合同、员工、访客、服务人员 |
| 授权审批 | 可以 | 走平台工作流 |
| 授权冻结/撤销 | 可以 | 冻结、撤销、到期 |
| 人员钥匙包 | 可以 | 按人员聚合有效授权 |
| 授权履历 | 可以 | 申请、审批、变更、撤销、同步 |
| 授权统计 | 可以 | 按项目/空间/人员/设备统计 |

## 3. 不建议放进业务平台的部分

```text
卡片号
人脸照片/人脸特征
指纹/指静脉
密码
二维码凭证
设备本地权限
设备通信协议
设备下发指令
设备执行结果
IOT 凭证同步细节
```

这些属于 IOT 平台。

业务平台只维护“授权意图”，IOT 负责“凭证落地”。

---

## 4. 现有平台表可以直接复用

现有平台已经有：

```text
bp_grant_entitlement   授权关系
bp_grant_freeze        授权冻结
bp_grant_audit_log     授权审计
bp_grant_task          授权任务/同步
bp_grant_keyring       钥匙包/凭证
bp_grant_iot_person_map 人员与 IOT 映射
```

建议：

### 4.1 授权关系继续用 `bp_grant_entitlement`

它已经包含：

```text
holder_type
person_id
org_id
space_id
space_path
house_id
valid_start
valid_end
allow_open
allow_manage
allow_delegate
visit_limit_times
source_type
source_id
grant_status
freeze_reason
revoke_reason
```

这套模型本身就是平台级，不需要再建 `prop_grant`。

### 4.2 设备授权扩展

如果当前 `bp_grant_entitlement` 只到空间/房屋，可以增加：

```text
target_type   SPACE / DEVICE / DEVICE_GROUP
target_id     空间/设备/设备组 ID
device_id     可空
device_group_id 可空
```

或者保持空间授权为主，设备授权作为空间授权的补充。

建议优先级：

```text
空间授权优先
设备组授权次之
单设备授权作为例外
```

因为设备绑定在空间上，空间授权可以覆盖下级设备。

### 4.3 人员钥匙包

建议不要把 `bp_grant_keyring` 直接当业务钥匙包页面。

原因：

```text
bp_grant_keyring 包含 key_type、channel_type、channel_value、
verify_way、is_real 等 IOT 凭证字段
```

业务人员钥匙包只应展示：

```text
人员
项目
空间/设备
授权级别
有效期
来源
状态
是否已同步 IOT
```

建议：

```text
业务钥匙包 = 按 person_id 聚合 bp_grant_entitlement 的查询视图
bp_grant_keyring 继续作为 IOT 凭证表
业务页面不展示 channel_value、人脸、指纹、密码
```

如果确实需要“业务钥匙包”作为独立对象，可以增加：

```text
bp_grant_keyring_package
  person_id
  package_name
  package_status
  effective_from
  effective_to
```

但底层授权仍关联 `bp_grant_entitlement`。

### 4.4 审批

不建议在物业审核中心单独做一套授权审批。

建议：

```text
业务授权申请
→ 平台工作流 bp_wf_*
→ 通过后生成/更新 bp_grant_entitlement
→ 同步 IOT
```

`bp_grant_audit_log` 继续记录授权业务审计。

### 4.5 IOT 同步

业务平台：

```text
授权意图
授权有效期
授权范围
撤销/冻结
```

IOT 平台：

```text
凭证生成
凭证下发
设备执行
执行结果
```

同步状态：

```text
PENDING
SYNCING
SYNCED
FAILED
```

业务页面显示同步状态，但不直接操作设备。

## 5. 目标分层

```text
平台授权能力
├─ bp_grant_entitlement   人员/空间/设备授权
├─ bp_grant_freeze        冻结
├─ bp_grant_audit_log     业务审计
├─ bp_grant_task          同步任务
├─ bp_wf_*                授权审批
└─ 业务钥匙包视图          按人员聚合授权

IOT 平台
├─ 卡片/人脸/指纹/密码
├─ 凭证下发
├─ 设备执行
└─ 设备本地权限

场景层
├─ prop_*       物业授权入口、物业设备/空间
├─ guarantee_*  保障房授权入口
└─ park/campus_* 其他场景入口
```

---

## 6. 页面建议

### 6.1 设备授权

```text
设备授权
├─ 按人员授权
├─ 按空间授权
├─ 按设备组授权
├─ 单设备授权（例外）
├─ 授权审批
├─ 冻结/撤销
└─ 授权履历
```

### 6.2 人员钥匙包

```text
人员钥匙包
├─ 人员基本信息
├─ 当前有效授权
├─ 已过期授权
├─ 已冻结/撤销
├─ 授权来源
├─ 生效时间
├─ 同步状态
└─ 操作：申请/续期/撤销
```

不展示：

```text
卡号
人脸
指纹
密码
二维码
```

## 9. 与现有保障房授权的关系

现有保障房已经有：

```text
人员授权
钥匙包
通行授权
授权记录
```

物业不应另建一套。

建议：

```text
保障房、物业、园区、校园共用 bp_grant_entitlement
场景只做入口、筛选、表单和权限
物业设备授权复用平台授权
```

这样不会出现：

```text
保障房一套授权
物业一套授权
园区一套授权
```

## 10. 优先级

### P0

```text
人员空间授权
设备组授权
授权有效期
授权审批
授权撤销/冻结
人员钥匙包查询
```

### P1

```text
单设备授权
授权续期
授权统计
IOT 同步状态
授权到期提醒
```

### P2

```text
批量授权
按合同自动授权
按人员组授权
授权策略模板
```

---

## 11. 结论

```text
设备授权可以升级为平台能力
人员钥匙包可以作为平台授权聚合视图
但不做具体钥匙/卡片/人脸/指纹/密码授权
```

边界：

```text
平台决定“谁可以进哪个空间/设备”
IOT 决定“用什么凭证、怎么下发、设备怎么执行”
```

建议复用：

```text
bp_grant_entitlement
bp_grant_freeze
bp_grant_audit_log
bp_grant_task
```

不要新建物业专属授权表。
