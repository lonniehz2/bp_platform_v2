# 多场景平台框架落地路线

## 保障房第一场景，物业 V1 第二场景

> 结论：可以，但保障房应采用“平台适配 + 渐进改造”，不建议整体重写  
> 目标：先做平台框架，保障房作为第一个场景验证，物业 V1 作为第二个场景落地，其他场景后续扩展
>
> **当前第一优先级：保障房管理平台；物业 V1 排第二。**

---

## 1. 总体判断

可以做，而且保障房适合作为第一个场景，因为：

```text
保障房已经运行
有真实组织、空间、房源、人员、合同、审批、账单、设备、授权
能验证平台能力是否真的可复用
能暴露物业设计中过度抽象的地方
```

但不建议：

```text
把保障房现有系统整体推倒重写
把所有保障房表改成 bp_ 前缀
先做完整保障房迁移，再开始物业 V1
```

推荐：

```text
平台框架先设计
保障房做场景注册和适配
物业 V1 在平台上落地
保障房深度能力按切片迁移
```

---

## 2. 目标形态

```text
多场景平台
├─ 平台基础能力
├─ 平台业务能力
├─ 场景包
│  ├─ GUARANTEE 保障房
│  ├─ PROPERTY 物业
│  ├─ APARTMENT 公寓
│  ├─ OFFICE 办公楼
│  ├─ HOTEL 酒店
│  ├─ BNB 民宿
│  ├─ ONLINE_RENTAL 网约房
│  ├─ DORMITORY 宿舍
│  └─ CAMPUS 校园
└─ 独立系统
   ├─ IOT
   └─ 智慧停车
```

保障房不是“平台”，而是平台上的第一个场景包。

物业 V1 是第二个场景包。

---

## 3. 核心原则

### 3.1 平台不依赖场景

```text
平台表不出现 guarantee_/prop_ 外键
平台接口不返回场景专属字段
平台能力通过 scene_code、biz_type、policy 扩展
```

### 3.2 保障房先适配，不先重写

```text
保留现有菜单、路由、表、接口
增加场景注册和适配层
低风险能力先接入平台
高风险能力后迁移
```

### 3.3 物业 V1 不等待保障房全部迁移

```text
平台框架完成后
保障房场景注册和基础适配先做
物业 V1 可以开始第二个场景落地
保障房合同/账单/审批可以按切片继续迁移
```

### 3.4 渐进迁移

```text
先只读
再双写/适配
再切换
最后清理旧逻辑
```

每一步都要有回滚。

---

## 4. 保障房场景映射

| 能力 | 保障房现状 | 平台化处理 | 迁移方式 |
|---|---|---|---|
| 租户/组织 | 已有 | 复用 | 不动 |
| 项目/小区 | bp_iam_org | 增加 scene_code/business_mode | 增量字段 |
| 空间 | bp_asset_space | 空间模板、资产类型 | 增加模板选择，不重建空间 |
| 房源 | bp_asset_house | 平台房屋主档 + 场景扩展 | 保留现有表，增加扩展 |
| 人员 | bp_person | 平台人员主档 | 复用 |
| 人员关系 | 保障房现有关系 | 通用关系框架 + 场景扩展 | 适配 |
| 合同 | biz_contract | 平台合同生命周期 | 适配器，不立即换表 |
| 合同变更/退租/换房 | biz_* | 平台工作流 + 场景业务 | 逐步接入 |
| 审批 | 现有审批逻辑 | bp_wf_* | 新流程走平台，旧流程兼容 |
| 账单/财务 | bp_fin_* | 平台计费内核 | 先适配接口，不重写 |
| 补贴 | 现有补贴 | 平台优惠/补贴引擎 | biz_type 区分 |
| 设备 | bp_dev_device | 设备资产平台能力 | 增量字段 |
| 授权 | bp_grant_* | 平台授权/钥匙包 | 复用 |
| 消息/文件/字典 | 已有 | 复用 | 不动 |
| 报表 | 现有报表 | 平台报表框架 | 逐步迁移 |

关键：

```text
保障房现有表先保留
平台能力通过适配器接入
不要求第一步就把 biz_contract/bp_fin_bill 换成平台表
```

## 8. 保障房适配步骤

### Step 1：场景注册

```text
保障房项目增加 scene_code=GUARANTEE
现有项目增加 business_mode
不改变现有页面行为
```

### Step 2：空间/资产适配

```text
保障房空间模板：
  基础：小区/楼栋/单元/楼层/房屋
  可选：床位
  可选：内房/床位
资产类型：公租房/保租房/人才公寓/宿舍
现有空间数据不重建
```

### Step 3：人员/授权适配

```text
人员主档复用
保障对象/家庭成员/承租人/同住人关系
授权复用 bp_grant_*
设备资产复用 bp_dev_device
```

### Step 4：审批适配

```text
新审批走 bp_wf_*
旧审批保留兼容
```

### Step 5：合同/账单适配

```text
合同：平台生命周期 + 保障房条款
账单：平台计费内核 + 保障房租金/补贴策略
```

### Step 6：菜单/角色

```text
保障房场景菜单
角色模板
物业场景菜单
角色模板
```


## 10. 推荐实施顺序

### Phase 0：平台框架设计

```text
场景包/经营模式
空间/资产模型
人员关系
合同/订单/住宿
计费/结算
工作流
设备/授权
菜单/角色
数据归属
ER/DDL 框架
```

### Phase 1：保障房场景注册和基础适配

```text
场景注册
空间模板/资产类型
人员/关系
设备/授权
不改变现有核心业务
```

### Phase 2：物业 V1 落地

```text
使用平台框架
物业场景包
收费闭环
```

### Phase 3：保障房深度适配

```text
审批
合同
账单
补贴
按切片迁移
```

### Phase 4：其他场景

```text
公寓/出租房
办公楼
酒店/民宿/网约房
宿舍/校园
```

说明：

```text
保障房是第一个场景，但不要求所有保障房能力迁移完才启动物业
物业 V1 可以在平台框架稳定后开始
保障房深度迁移与物业并行
```

---

## 11. 不建议的做法

```text
先重写保障房
把所有保障房表改成平台表
先做完整保障房迁移再开始物业
平台表直接引用 biz_*/bp_fin_*
为了物业方便改坏保障房
```

---

## 12. 风险与控制

| 风险 | 控制 |
|---|---|
| 保障房回归风险 | 保留旧路由/接口，逐步切换 |
| 数据迁移风险 | 先只读、双写、对比、切换 |
| 抽象过度 | 物业 V1 作为第二个场景验证 |
| 两套审批 | 新流程平台化，旧流程兼容 |
| 账单迁移风险 | 先适配，不直接替换 |
| 菜单混乱 | 场景包 + 角色模板 |
| 数据归属不清 | bp_/prop_/guarantee_ 明确 |

---

## 13. 结论

```text
可以先把保障房作为第一个场景落地
但要采用“平台适配 + 渐进改造”
不是整体重写保障房
```

推荐：

```text
平台框架设计
→ 保障房场景注册和基础适配
→ 物业 V1 第二个场景落地
→ 保障房深度迁移按切片继续
→ 其他场景后续扩展
```

这样既能用保障房验证平台框架，又不会因为保障房历史包袱拖慢物业 V1。
