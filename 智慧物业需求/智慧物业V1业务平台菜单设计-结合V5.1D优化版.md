# 智慧物业 V1 业务平台菜单设计（结合 V5.1D 优化版）

> 参考文件：`云门道智慧云功能菜单设计V5.1D.xls`  
> 重点参考工作表：`wy智慧云菜单（智慧物业场景）`、`人员类型与用户角色`、`资产建筑初始化`、`地址信息`  
> 范围前提：IOT 设备平台不纳入本期业务平台；智慧停车作为独立一级菜单保留，运营后续独立系统  
> 结论：在现有 9 组菜单基础上，调整为 **12 组菜单**，新增独立一级菜单“智慧停车”，其他重点补“基础配置、审核中心、供应商管理、资产异常、催收清单、空间结构模板”

## 1. V5.1D 菜单观察

V5.1D 的智慧物业场景共有 **22 个一级菜单**：

```text
1  系统管理
2  基础配置中心
3  策略中心
4  人员中心
5  资产中心
6  设备中心
7  审核中心
8  日志中心
9  授权管理
10 业主管理
11 访客管理
12 租赁管理
13 停车管理
14 能源管理
15 供应商管理
16 财务中心
17 智慧服务
18 智慧消防
19 智慧安防
20 智慧巡更
21 智慧保洁
22 智慧控制台
```

它的特点是：

1. **配置与业务分开**
   - 基础配置中心
   - 策略中心
   - 系统管理

2. **审核独立**
   - 实名审核
   - 业主审核
   - 访客邀请审核
   - 退款审核
   - 资产审核

3. **资产模型可配置**
   - 资产结构模型选择
   - 最多 6 层
   - 期/苑/幢/单元/楼层/房号可以按项目选择

4. **人员类型和角色分得很细**
   - 人员类型：业主、共用人、承租人、同住人、临时人员、访客
   - 组织角色：系统管理员、物业经理、财务主管、信息主管、客服主管、工程主管、保安主管、保洁主管、供应商负责人

5. **业主服务、租客、供应商、财务各自成体系**
   - 业主服务
   - 租客管理
   - 供应商管理
   - 财务中心

6. **实用查询做得细**
   - 资产查询
   - 催收查询
   - 资产异常警示
   - 出租记录
   - 转租分析

7. **日志独立**
   - 人员出入
   - 车辆出入
   - 资产授权
   - 设备授权
   - 系统操作
   - 数据备份

8. **服务与互动内容多**
   - 报修
   - 综合报修
   - 投诉建议
   - 公告通知
   - 装修管理
   - 搬家管理
   - 投票
   - 紧急联系人
   - APP 反馈

## 2. 最值得吸收的设计

### 2.1 增加“基础配置中心”

当前设计把很多配置放在“系统与数据”里，导致：

- 项目初始化时找不到配置入口
- 系统管理员和项目经理职责混在一起
- 字典、人员类型、资产结构、收费策略散落

建议单独设 **基础配置**：

```text
空间结构模板
资产类型/性质/状态
资产要素
人员类型
岗位
收费分类
行政区划/字典
```

其中最重要的是 **空间结构模板**。

### 2.2 空间层级改为“模板驱动”

V5.1D 的资产结构模型支持最多 6 层，并按场景选择：

```text
小区 A：期 → 苑/幢 → 单元 → 楼层 → 房号
小区 B：期 → 苑/幢 → 单元 → 楼层 → 房号 → 子房号
商业：楼 → 楼层 → 商铺号
办公：楼 → 楼层 → 房间
场地：区域 → 点位
```

我们当前设计是固定的“楼栋 → 单元 → 楼层 → 房间”，建议改为：

```text
项目
→ 按项目选择空间模板
→ 模板定义 1～6 级名称
→ 每级可配置是否必填
→ 最后一级挂房屋/商铺/办公/场地
```

技术上继续使用 `bp_asset_space` 的树形结构，增加：

```text
prop_space_template
  template_code
  template_name
  asset_type
  levels_json
  status
```

`levels_json` 示例：

```json
[
  {"level": 1, "name": "期", "required": false},
  {"level": 2, "name": "苑/幢", "required": true},
  {"level": 3, "name": "单元", "required": false},
  {"level": 4, "name": "楼层", "required": true},
  {"level": 5, "name": "房号", "required": true},
  {"level": 6, "name": "子房号", "required": false}
]
```

这样住宅、商业、办公、场地可以共用一套空间模型。

### 2.3 增加“审核中心”

V5.1D 把审核集中管理，比把审核散落在各业务页面更合理。

建议增加：

```text
审核中心
├─ 业主审核
├─ 实名审核
├─ 合同审核
├─ 优惠审核
├─ 退款审核
├─ 资产异常审核
└─ 访客邀请审核
```

好处：

- 项目经理/财务/客服有统一待办
- 审核权限集中
- 业务页面只负责发起，不负责审批
- 与工作台“我的待办”天然打通

### 2.4 增加“供应商管理”

物业实际大量使用外部供应商：

```text
保洁
保安
电梯维保
消防维保
绿化
维修
装修
```

建议在“服务与监督”下增加：

```text
供应商管理
├─ 服务商资源
├─ 签约服务商
├─ 服务人员
├─ 服务订单
├─ 维修费订单
└─ 服务评价
```

### 2.5 增加“催收清单”和“资产异常”

V5.1D 有两个很实用的页面：

```text
催收查询
资产异常警示
```

建议：

```text
收费与账务
└─ 催收清单
   ├─ 按楼栋/单元/房号排序
   ├─ 物业费、能耗费、租金合并
   ├─ 可打印上门催收
   └─ 关联催缴记录

项目与资产
└─ 资产异常
   ├─ 空置异常
   ├─ 转租/转借
   ├─ 长期无人
   └─ 异常处置
```

### 2.6 增加“人员组”

V5.1D 有：

```text
人员组信息
服务对象组
服务人员组
```

建议增加：

```text
客户与人员
└─ 人员组管理
   ├─ 业主组
   ├─ 租客组
   ├─ 服务人员组
   └─ 自定义组
```

用于：

- 按楼栋/单位分组
- 批量通知
- 批量收费
- 批量授权（后续 IOT）
- 服务人员排班

### 2.7 人员类型与角色重新梳理

V5.1D 的人员类型：

```text
业主
业主资产共用人
承租人
同住人
临时人员
访客
```

组织角色：

```text
系统管理员
物业经理
财务主管
信息主管
客服主管
工程主管
保安主管
保洁主管
供应商负责人
```

建议我们的角色矩阵补充：

```text

PROPERTY_SECURITY_SUPERVISOR 保安主管
PROPERTY_CLEANING_SUPERVISOR 保洁主管
SUPPLIER_MANAGER            供应商负责人
```

即使 IOT 和停车不纳入本期，保安、保洁、供应商仍然存在于物业服务中，只是他们使用的业务菜单较少。

### 2.8 增加“装修管理、搬家管理、报事、综合报修”

V5.1D 的“智慧服务”很贴近物业实际：

```text

报事
投诉建议
公告通知
```

## 5. 关键设计调整

### 5.1 项目地址从“五级地址”扩展为标准地址

V5.1D 的地址信息包含：

```text
省
市
区县
街道
社区
街/路/巷/里
门牌号
小区/建筑物
```

建议项目中文地址字段采用：

```text
省 / 市 / 区县 / 街道 / 社区
+ 街路巷
+ 门牌号
+ 小区/建筑物
+ 详细地址
```

仍然是五级行政区划，但增加街路巷、门牌号、建筑物，满足合同、收据、发票和备案地址。

### 5.2 组织层级与项目层级

保留：

```text
物业公司
→ 区域/城市公司
→ 物业项目
→ 服务处/管理处（可选）
```

项目节点：

```text
orgType = PROPERTY_PROJECT
五级地址 + 详细地址
```

### 5.3 资产结构模板

新增：

```text
prop_space_template
```

项目创建时选择模板，后续空间树按模板生成。

规则：

```text
空间结构模板按项目独立选择
不同项目可以使用不同模板
项目创建后，模板变更只影响尚未生成的空间
已生成空间保留原层级，不做自动重构
模板最多 6 级，至少 2 级
```

建议默认模板：

```text
住宅小区：期 → 苑/幢 → 单元 → 楼层 → 房号
商业：楼 → 楼层 → 商铺号
办公：楼 → 楼层 → 房间
场地：区域 → 点位
```

### 5.4 人员类型与关系

人员主档不写死类型，关系表表达：

```text
OWNER        业主
FAMILY       家人/共用人
TENANT       承租人
COHABITANT   同住人
TEMPORARY    临时人员
VISITOR      访客
SERVICE      服务人员
STAFF        物业工作人员
SUPPLIER     供应商人员
```

#### 人员信息字段

人员档案除姓名、证件、手机号、人员类型、实名状态外，增加：

```text
人脸照片 face_photo_url
```

规则：

```text
非必填，不阻塞人员建档
只存文件 URL，不存 base64
支持上传、预览、替换、移除
仅在人员详情、审核详情展示
列表不展示照片缩略图
本期只做照片存档，不做人脸识别、不做门禁下发
后续对接 IOT 时再定义下发、同步、删除规则
```

### 5.5 审核中心统一审批

审批类型：

```text
OWNER_VERIFY       业主审核
REALNAME_VERIFY    实名审核
CONTRACT_APPROVE   合同审核
DISCOUNT_APPROVE   优惠审核
REFUND_APPROVE     退款审核
ASSET_EXCEPTION    资产异常审核
VISITOR_APPROVE    访客邀请审核
```

统一待办、统一记录、统一权限。

审批支持：

```text
单级审批
多级串行审批
平级多人审批
会签：所有人通过才通过
或签：任意一人通过即通过
金额分级审批
```

审批配置：

```text
审核类型
项目
金额区间
审批节点
节点审批人/角色
串行/并行
会签/或签
```

审核任务记录：

```text
当前节点
当前审批人
审批历史
审批意见
审批时间
```

### 5.6 收费策略与计费方案

保留：

```text
收费项目
计费方案
优惠与补贴
```

不建议单独做很重的“策略中心”一级菜单，除非后续策略类型继续增加。

收费项目类别固定为：

```text
物业费
能耗费
水费
电费
车位管理费
租金
其他
```

说明：

```text
物业费：按建筑面积
能耗费：公摊/公共能耗
水费：水表用量
电费：电表用量
车位管理费：按车位/车辆收取；停车运营由独立系统负责，
            业务平台只保留收费类别和账单接口
租金：商铺/办公/场地/广告位等租赁
其他：多经收入、其他收入等
```

如果后续收费策略复杂，可以把以下放进“收费项目/计费方案”的二级页：

```text
物业费计价策略
能耗费计价策略
公摊策略
滞纳金策略
优惠策略
```

### 5.7 资产类型与差异化计费

房屋、车位、场地不能只按“项目”定一个单价，需要按资产类型区分。

#### 资产类型

房屋：

```text
RES_HIGH_RISE     高层住宅
RES_MULTI         多层住宅
RES_TOWNHOUSE     排屋/别墅
COMMERCIAL        商业
SHOP              商铺
OFFICE            办公
WAREHOUSE         仓库
PUBLIC_FACILITY   公共配套
```

车位：

```text
PARKING_GARAGE       车库车位
PARKING_OPEN         露天车位
PARKING_UNDERGROUND  地下车位
PARKING_EV           充电车位
```

资产类型建议做成**租户级**可配置字典，不写死在代码里。

规则：

```text
资产类型是租户级字典
同一租户下的多个项目共用
项目不能重复定义同名类型
项目可以引用、启用/停用类型
不同项目通过计费方案设置不同单价
```

#### 资产上的类型字段

```text
bp_asset_space.asset_type_code       楼栋默认资产类型（可空）
prop_unit_ext.asset_type_code        房屋资产类型
prop_parking_space.asset_type_code   车位资产类型
```

继承规则：

```text
房屋有类型 → 用房屋类型
房屋没有 → 用楼栋默认类型
楼栋没有 → 用项目默认类型
```

#### 计费方案范围

`prop_billing_scheme` 的 `scope_type` 增加：

```text
PROJECT      项目
ASSET_TYPE   资产类型
BUILDING     楼栋
HOUSE        房屋/车位
```

示例：

```text
高层住宅物业费：2.20 元/㎡/月
多层住宅物业费：1.80 元/㎡/月
排屋物业费：3.00 元/㎡/月
商业物业费：5.00 元/㎡/月

高层能耗费：0.50 元/㎡/月
商业能耗费：1.20 元/㎡/月

车库车位管理费：100 元/月
露天车位管理费：60 元/月
```

#### 取价优先级

同一收费项目、同一期间，按最具体范围取价：

```text
HOUSE > BUILDING > ASSET_TYPE > PROJECT
```

规则：

```text
房屋/车位单独配置优先
楼栋配置次之
资产类型配置次之
项目默认最后

同一范围、同一收费项目、同一时间不能重复生效
没有匹配方案时不允许出账，并提示配置缺失
```

#### 按面积计费

```text
金额 = 建筑面积 × 单价 × 月数
```

单价来自：

```text
收费项目默认价
或 资产类型方案价
或 楼栋/房屋覆盖价
```

#### 按表计费

```text
金额 = 用量 × 单价
```

水费、电费也可以按资产类型设置不同单价：

```text
居民用电：0.60 元/度
商业用电：0.90 元/度
居民用水：3.50 元/吨
商业用水：4.50 元/吨
```

#### 车位收费

车位管理费按车位资产类型取价：

```text
车库车位：100 元/月
露天车位：60 元/月
充电车位：120 元/月
```

本期停车运营仍归独立停车系统，业务平台只保留车位管理费收费类别和方案。

#### 公共能耗分摊

公共能耗分摊仍按建筑面积分摊，但可以按资产类型设置不同的分摊系数：

```text
分摊金额 = 公摊总额 × 房屋面积 × 资产类型系数 ÷ 项目加权面积
```

如果本期不做系数，先按面积平均分摊；后续再扩展。

### 5.8 合同选择计费方案

计费方案不直接替代合同，而是作为合同中的计费规则。

```text
合同
├─ 合同类型：租赁合同 / 物业服务合同 / 车位管理合同
├─ 合同主体：出租方/承租方、业主、项目
├─ 计费方案：选择一个或多个计费方案
│  ├─ 物业费方案
│  ├─ 能耗费方案
│  ├─ 水费方案
│  ├─ 电费方案
│  ├─ 车位管理费方案
│  └─ 租金方案
├─ 生效日期、结束日期
└─ 出账：按方案生成账单
```

账单来源：

```text
CONTRACT       合同 + 计费方案
METER          抄表
ENERGY_ALLOC   公摊
MANUAL         手工/多经
```

规则：

```text
租赁合同：选择租金方案，可附带物业费/能耗费方案
物业服务合同：选择物业费/能耗费等方案
车位管理合同：选择车位管理费方案
一份合同可以关联多个计费方案
账单记录 contract_id 和 scheme_id
合同变更时，可按生效日期切换计费方案
历史账单保留原方案快照
```

物业服务合同：

```text
物业服务合同按项目签订
签约方：业主委员会 / 资产方 / 产权单位
一个项目原则上有一份整体物业服务合同
合同覆盖项目或项目内部分资产
合同中选择物业费/能耗费等计费方案
不按每户生成物业服务合同
```

账单来源：

```text
物业费/能耗费账单
→ 关联项目物业服务合同
→ 关联具体计费方案
→ 关联房屋/资产类型
```

租赁合同仍然按租户/商铺/场地单独签订，和项目物业服务合同分开。

## 9. 结论

V5.1D 最值得学习的不是它的 22 个一级菜单，而是以下六个设计：

1. **配置、策略、业务、审核、日志分层**
2. **空间结构模板化，最多 6 层**
3. **审核中心统一审批**
4. **人员类型 + 组织角色分离**
5. **供应商管理独立**
6. **催收清单、资产异常、转租分析等实用查询**

结合我们已实现的收费闭环，最终采用 **12 组菜单**：

```text
工作台
项目与资产
客户与人员
合同与租赁
收费与账务
计量与能耗
服务与监督
审核中心
经营分析
基础配置
智慧停车
系统与数据
```

相比当前 9 组菜单，新增：

```text
审核中心
基础配置
智慧停车
供应商管理
资产异常
催收清单
对账管理
装修/搬家/综合报修
```

同时继续排除：

```text
IOT 设备平台
智慧消防/安防/巡更/保洁
平台开发工具
```

这样既保留了 V5.1D 的运营完整性，又符合本期业务平台的边界。
