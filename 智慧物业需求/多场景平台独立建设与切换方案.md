# 多场景空间资产运营平台独立建设与切换方案

> 问题：新平台是否需要单独目录、单独 Web 端口、单独数据库，先与保障房系统隔离，等保障房场景完成后再切换？  
> 结论：合理，但应定义为“过渡性隔离”，不是永久分叉成两套系统

---

## 1. 结论

建议采用：

```text
独立代码目录
+ 独立应用进程/端口
+ 独立数据库/schema
+ 独立 UAT 环境
+ 统一生产网关/子域名
+ 一次性切换，不长期双写
```

但目标仍然是：

```text
一个多场景平台
一个代码主线
一个生产入口
一个租户/权限体系
```

独立目录、端口、数据库是**过渡隔离**，不是最终产品分叉。

---

## 2. 推荐隔离方式

| 维度 | 建议 | 说明 |
|---|---|---|
| 代码目录 | 独立目录/仓库 | 新平台独立建设，不直接改老保障房代码 |
| 应用端口 | 独立端口 | 开发/UAT 并行运行 |
| 数据库 | 独立 schema/database | 新库 `bp_platform_v2`，不直接写老库 |
| Web 入口 | 生产统一网关/子域名 | 端口只是部署细节，不暴露给用户 |
| 用户体系 | 新平台独立租户/用户 | 不做长期共享 session |
| 文件存储 | 新平台独立 bucket/目录 | 迁移老附件，保留映射 |
| IOT | 继续走 IOT 平台接口 | 不复制 IOT 能力 |
| 停车 | 独立智慧停车系统 | 不放进业务平台库 |

## 4. 数据库策略

### 4.1 新平台一个库

建议：

```text
bp_platform_v2
```

一个库承载所有场景：

```text
bp_*          平台能力
guarantee_*   保障房场景
prop_*        物业场景
```

不建议：

```text
保障房一个库
物业一个库
酒店一个库
```

因为：

```text
跨场景统计困难
人员/组织/设备/合同难统一
平台能力无法共享
```

### 4.2 老库只读/迁移

```text
老库：bp_platform
新库：bp_platform_v2

迁移期间：
  老库只读
  新库写入
  按模块迁移
  不做长期双写
```

### 4.3 迁移顺序

```text
基础数据
租户/组织/项目/空间/房屋/人员
→ 业务数据
合同/账单/收款/设备/授权
→ 附件
文件/图片/合同附件
→ 历史日志
按需归档
```

### 4.4 迁移校验

```text
记录数
金额合计
合同数
账单数
收款数
设备数
授权数
附件数
抽样对照
```

## 5. Web 入口策略

### 开发/UAT

```text
老系统：http://host:8080
新平台：http://host:8090
```

用于并行开发、UAT、数据迁移验证。

### 生产

不建议让用户访问裸端口。

建议：

```text
https://guarantee.example.com
https://platform.example.com
```

或：

```text
https://platform.example.com
  → 租户/场景入口
```

通过 Nginx/网关路由，不暴露端口。

原则：

```text
端口是部署细节
子域名/网关是用户入口
不使用路径参数或 app 参数区分租户
```

## 6. 新平台建设方式

### 6.1 平台核心

```text
tenant/org/permission
scene_profile/business_mode
space template/asset type
person
device asset/authorization
workflow
contract/booking/stay
billing kernel
discount/subsidy
document
```

### 6.2 保障房场景

```text
guarantee 场景包
资格/轮候/配租/合同/补贴/退租
```

作为第一个场景，验证平台。

### 6.3 物业场景

```text
property 场景包
项目/房屋/业主/物业费/停车/能耗
```

作为第二个场景。

### 6.4 不复制老代码

```text
复用设计、表结构经验、业务规则
不直接 copy 老项目代码
不共享数据库连接
不共享 session
```

## 7. 切换方案

### Phase 0：隔离建设

```text
新目录
新端口
新数据库
新 CI/CD
```

### Phase 1：保障房场景完成

```text
基础数据迁移
核心业务迁移
UAT
```

### Phase 2：并行验证

```text
老系统只读或冻结写入
新系统试运行
数据对比
用户培训
```

### Phase 3：切换

```text
域名/网关切到新平台
老系统保留只读
观察期
```

### Phase 4：下线

```text
确认稳定
老系统归档
停止写入口
```

---

## 8. 风险与控制

| 风险 | 控制 |
|---|---|
| 两套系统长期并存 | 明确切换日期和下线条件 |
| 数据漂移 | 迁移后老库只读，不做长期双写 |
| 用户账号/权限差异 | 迁移映射表，强制改密或 SSO |
| 文件附件丢失 | 迁移文件并校验 URL/哈希 |
| 金额不一致 | 财务对账，保留差异清单 |
| 设备/IOT 映射 | 保留 iot_device_id 映射 |
| 报表口径变化 | 新旧报表并行对比 |
| 切换失败 | 老系统只读回退，不删除数据 |

---

## 9. 不建议的做法

```text
直接把新代码写进老保障房项目
新平台直接连老库读写
长期双写
把老代码复制一份改名
每个场景一个独立数据库
生产环境暴露裸端口
没有迁移校验就切换
```

---

## 10. 结论

```text
单独目录、单独端口、单独数据库：合理
但要定义为过渡隔离
最终仍是一个多场景平台
```

推荐：

```text
新平台独立目录/仓库
新应用端口
新数据库 bp_platform_v2
保障房作为第一个场景
物业作为第二个场景
老系统只读迁移
一次性切换
```

这样既能避免新老系统互相污染，又不会形成永久两套系统。
