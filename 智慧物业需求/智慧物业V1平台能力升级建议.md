# 智慧物业 V1 平台能力升级建议

> 目的：从智慧物业设计中识别可复用、可跨场景沉淀的平台能力
>
> 全面总规见：[智慧物业V1平台能力总体规划](智慧物业V1平台能力总体规划.md)  
> 范围：平台基础能力、平台业务能力、物业场景能力、独立系统边界  
> 原则：只升级稳定、跨场景、可扩展的能力，不把物业专属逻辑硬抽成平台

---

## 1. 判断标准

一个设计适合升级为平台能力，需要同时满足：

```text
1. 至少两个场景需要
   保障房、物业、园区、校园、公寓等

2. 语义稳定
   不是某个场景的临时业务规则

3. 有清晰扩展点
   平台提供框架，场景提供策略/表单/字段

4. 不依赖物业专属表
   不能 platform 表反向依赖 prop_* 表

5. 可以渐进迁移
   不影响现有保障房和物业运行
```

不满足以上条件的，继续留在物业域，不强行平台化。

## 2. 已经具备的平台能力

以下能力已经是平台级，物业设计应复用，不再另建：

```text
租户
组织
用户
角色
权限
数据范围
行政区划
字典
文件上传
消息中心
短信/微信通道
设备
空间
房源
人员主档
租户域名/子域名
操作日志
```

空间结构模板和资产类型本次已经升级为平台级：

```text
bp_asset_space_template
bp_asset_type
```

## 3. 建议升级为平台能力的设计

### 3.1 审批/工作流能力

优先级：**P0，最建议升级**

物业设计中有：

```text
prop_audit_flow
prop_audit_node
prop_audit_task
prop_audit_record
```

它不只服务物业：

```text
保障房：合同变更、退租、换房、资格复核
物业：业主审核、合同审核、优惠、退款
园区：入驻审核、装修审核
其他：供应商签约、采购审批
```

建议升级为：

```text
bp_wf_flow
bp_wf_node
bp_wf_task
bp_wf_record
```

平台提供：

```text
单级审批
多级串行
平级多人
会签 ALL
或签 ANY
金额分级
审批历史
待办集成
```

场景提供：

```text
业务类型
业务表单
金额字段
审批人角色
节点名称
```

结论：

```text
审核中心是物业页面
审批引擎是平台能力
不要为物业单独造一套审批表
```

### 3.2 合同生命周期框架

优先级：**P1**

共性能力：

```text
合同模板
合同起草
合同审批
合同签署
合同生效
合同变更
合同续签
合同终止
附件
履约提醒
合同台账
```

场景差异：

```text
保障房：租赁合同、资格条件、租金标准
物业：物业服务合同、商铺/场地租赁合同
园区：入驻合同、服务合同
```

建议：

```text
bp_contract          合同主表/框架
bp_contract_change   合同变更
bp_contract_file     合同附件
bp_contract_term     场景合同条款（JSON 或扩展表）
```

物业专属保留：

```text
prop_service_contract  项目物业服务合同
prop_lease_contract    物业租赁合同扩展
```

不要一开始强行把所有合同字段统一，先统一生命周期和审批。

### 3.3 计费/收费内核

优先级：**P1，价值高但复杂度高**

可平台化的部分：

```text
账单主表
账单明细
收款
收款分摊
收据
发票申请
欠费
催缴任务
资金流水
```

物业/保障房差异：

```text
收费项目
计价规则
优惠/补贴
合同来源
账单展示
```

建议分层：

```text
bp_billing_kernel      账单、收款、分摊、收据、发票、流水
bp_billing_policy      计费策略接口
场景策略               物业费/租金/保障房租金/补贴
```

不建议本期直接把 `prop_bill` 全量替换为平台账单，风险太大。

建议先做：

```text
统一收款/收据/发票/流水接口
统一账单编号与幂等
统一账单状态机
物业账单继续用 prop_bill，通过适配器接入
```

后续再评估是否合并 `bp_fin_bill` 和 `prop_bill`。

### 3.4 优惠/补贴/减免引擎

优先级：**P1**

共性能力：

```text
优惠类型
适用范围
优惠方式：比例/固定金额/免单
生效期
审批
抵扣记录
报表口径
```

场景差异：

```text
物业优惠：开业优惠、长租优惠、老业主优惠
政府补贴：保障房租金补贴、人才补贴
```

建议：

```text
bp_discount_policy
bp_discount_grant
bp_discount_usage
```

通过：

```text
biz_type = PROPERTY_DISCOUNT / GOV_SUBSIDY
scene_code = PROPERTY / GUARANTEE / PARK
```

区分资金口径、审批流程和报表。

不建议直接把政府补贴表当物业优惠表使用。

### 3.5 供应商/服务商主数据

优先级：**P2**

可平台化：

```text
供应商档案
服务类别
服务人员
签约状态
评价
黑名单
```

场景差异：

```text
物业：保洁、保安、电梯维保、维修
保障房：维修、评估、法律服务
园区：保洁、绿化、安保
```

建议：

```text
bp_supplier
bp_supplier_staff
```

物业保留：

```text
prop_supplier_order
prop_service_order
```

供应商主数据平台共用，服务订单按场景扩展。

### 3.6 人员标签/人员组

优先级：**P2**

可平台化：

```text
人员标签
人员组
组成员
批量通知
批量授权
```

场景差异：

```text
物业：业主组、租客组、服务人员组
保障房：轮候组、保障对象组、审核组
园区：员工组、访客组
```

建议：

```text
bp_person_tag
bp_person_group
bp_person_group_member
```

物业保留业务含义和页面。

### 3.7 文档/PDF/打印模板

优先级：**P2**

可平台化：

```text
模板管理
变量替换
PDF 生成
打印
水印
验真
归档
```

场景差异：

```text
物业：收据、缴费通知、催缴单
保障房：合同、告知书、公示文件
```

建议：

```text
bp_doc_template
bp_doc_render
bp_doc_archive
```

PDF 渲染、字体、水印、验真是平台能力；收据/合同内容是场景模板。

### 3.8 统一导入导出/报表/查询

优先级：**P2**

可平台化：

```text
Excel 导入
模板校验
错误行回写
导出任务
报表订阅
统一查询
```

场景差异：

```text
物业：房屋、业主、账单、催收清单
保障房：申请、合同、轮候
```

建议：

```text
bp_import_task
bp_export_task
bp_report_template
bp_search_index
```

不要每个场景各写一套导入导出。

## 4. 应继续留在物业域的设计

以下不建议平台化：

```text
业主/住户关系
房屋资产类型细分
物业费计价规则
能耗费公摊规则
车位管理费规则
物业服务合同条款
物业收费项目分类
物业利润表
物业催收清单
物业公告/投票/装修/搬家
```

原因：

```text
强物业业务语义
跨场景抽象会变成大量 if/else
```

保留：

```text
prop_owner_unit
prop_unit_ext
prop_billing_scheme
prop_service_contract
prop_fee_item
prop_energy_allocation
```

## 5. 独立系统，不做平台业务能力

```text
IOT 设备平台
智慧停车
智慧消防
智慧安防
智慧巡更
智慧保洁
```

这些是独立系统或外部平台，不做进物业业务平台。

业务平台只保留接口：

```text
IOT：表计读数、设备状态、告警
停车：车位、车辆、停车订单、停车收入
```

## 6. 目标分层架构

```text
平台基础层
├─ bp_iam_*          租户/组织/用户/角色/权限
├─ bp_asset_*        空间模板/资产类型/空间/房源
├─ bp_person         人员主档
├─ bp_msg_*          消息/短信/微信
├─ bp_file           文件/照片
├─ bp_dict/region    字典/区划
├─ bp_wf_*           审批/工作流
├─ bp_doc_*          PDF/模板/打印
└─ bp_log           操作日志

平台业务层
├─ bp_contract_*     合同生命周期
├─ bp_billing_*      账单/收款/收据/发票内核
├─ bp_discount_*     优惠/补贴引擎
└─ bp_supplier_*     供应商主数据

场景层
├─ prop_*            物业费、公摊、业主关系、物业合同、物业报表
├─ guarantee_*       保障房资格、轮候、配租、补贴
└─ park/campus_*     园区/校园扩展

独立系统
├─ IOT 平台
└─ 智慧停车
```

## 7. 当前设计需要调整的地方

### 7.1 审批表

从：

```text
prop_audit_flow
prop_audit_node
prop_audit_task
prop_audit_record
```

调整为：

```text
bp_wf_flow
bp_wf_node
bp_wf_task
bp_wf_record
```

物业审核中心只做：

```text
业务表单
业务类型
金额
审批人角色
待办展示
```

### 7.2 供应商

从：

```text
prop_supplier
prop_service_staff
```

调整为：

```text
bp_supplier
bp_supplier_staff
```

物业保留服务订单。

### 7.3 计费

本期保持：

```text
prop_bill
prop_payment
prop_receipt
prop_invoice
```

但接口设计按平台内核抽象：

```text
BillingKernel
PaymentKernel
ReceiptKernel
```

后续再评估是否合并保障房账单和物业账单。

### 7.4 优惠

从物业独立的优惠表，调整为：

```text
bp_discount_policy
bp_discount_grant
bp_discount_usage
```

通过 `biz_type` 区分物业优惠和政府补贴。

### 7.5 文档/收据

本期可以继续用物业 PDF 服务，但建议抽出：

```text
bp_doc_render
```

后续收据、催缴单、合同、告知书共用。

## 8. 优先级建议

### P0：编码前就要定

```text
空间结构模板平台化
资产类型平台化
审批/工作流平台化
文件/照片平台化
```

### P1：可以与物业编码并行设计

```text
合同生命周期框架
计费/收费内核
优惠/补贴引擎
```

### P2：后续逐步沉淀

```text
供应商主数据
人员标签/人员组
文档/PDF
导入导出/报表/查询
```

## 9. 结论

从物业设计中最值得升级为平台能力的是：

```text
1. 空间结构模板 + 资产类型（已升级）
2. 审批/工作流（最建议）
3. 合同生命周期框架
4. 计费/收费内核
5. 优惠/补贴引擎
6. 供应商主数据
7. 人员标签/人员组
8. PDF/文档/打印模板
9. 导入导出/报表/统一查询
```

但要坚持：

```text
平台提供框架
场景提供策略
物业专属逻辑不强行抽象
不为了平台化而平台化
```

下一步建议先改 ER/DDL：

```text
prop_audit_* → bp_wf_*
prop_supplier → bp_supplier
优惠表 → bp_discount_*
```

再进入编码准备。

## 10. 设备业务能力

业务平台中的设备内容也可以升级为平台能力，但只包括设备资产台账、空间绑定、责任归属、业务状态、运维履历、设备组/类型、二维码。

不包括 IOT 平台的设备通信、控制、告警、门禁、卡片和实时状态。

详见：[智慧物业V1设备业务平台能力建议](智慧物业V1设备业务平台能力建议.md)

设备授权和人员钥匙包见：[智慧物业V1设备授权与钥匙包平台能力建议](智慧物业V1设备授权与钥匙包平台能力建议.md)
