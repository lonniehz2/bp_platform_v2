## 2. 值得参考的地方

### 2.1 设备中心比我们设计得更细

云门道把设备拆成了：

```text
设备管理
设备组管理
采集器管理
智能柜管理
设备列表
门锁列表
换锁日志
设备入库
```

其中特别值得参考：

1. **设备组**
   - 按项目、楼栋、设备类型分组
   - 便于批量授权、批量告警、批量运维

2. **采集器/网关**
   - 采集器不是普通设备
   - 需要独立管理在线状态、下挂设备、通信质量

3. **换锁/换表日志**
   - 设备更换是物业实际高频场景
   - 只看设备台账不够，需要保留更换历史

4. **设备入库**
   - 门禁、门锁、梯控、车闸、采集器、车闸盒子、水电表、网关分别入库
   - 对应设备生命周期的“采购/入库/安装/启用”

5. **远程开门/远程控制**
   - 物业客服、保安、工程都需要
   - 必须留操作日志和权限控制

### 2.2 通行管理比我们设计得更完整

云门道有：

```text
卡片管理
钥匙卡信息

开门记录
人脸开门记录

```

我们目前设计中有“钥匙包”，但缺少：

- 实体卡/钥匙卡管理
- 制卡记录
- 按人员、按组授权
- 长期未开门异常

```text

车牌
```

## 3. 不建议直接照搬的地方

### 3.1 不适用的行业模块

```text
酒店房源管理
学校房屋管理
健康码记录
防疫通行日志
```

这些是特定行业/历史功能，不建议进入物业 V1 主菜单。

### 3.2 平台级功能

```text
财务管理(平台)
开发工具
第三方数据导入
身份查询
设备入库中的采购入库
```

这些更适合平台运营/实施团队，不适合物业公司普通用户。

### 3.3 过度安防模块

```text
智慧安防（布控研判）
人脸识别轨迹跟踪
```

涉及隐私和合规，建议作为独立扩展包，不进入 V1 默认菜单。

### 3.4 会议管理

```text
会议室管理
会议预约管理
```

物业公司内部会议可以使用，但不是物业核心业务，建议作为可选模块。

### 3.5 菜单不要照抄 33 个一级菜单

云门道的菜单是按 IOT 平台能力展开的，一级菜单过多。

我们的智慧物业应保持 10～11 个一级菜单，把它的能力合并进现有分组。

## 8. 结论

云门道平台最值得参考的不是它的 33 个一级菜单，而是它在以下四个方面的**运营深度**：

1. **设备与通行的全生命周期**
   - 设备组、采集器、网关、卡片、授权、开门记录、换锁日志、远程开门。

2. **停车运营**
   - 车辆、订单、临停策略、车闸、停车券、异常抬杆、在场状态。

3. **能源运营**
   - 远程控制、日冻结、换表日志、缴费户号。

4. **服务与互动**
   - 公告、投票、投诉、联系物业、APP 反馈、安装/维保人员。

对智慧物业 V1 的建议是：

```text
保留我们已有的收费、账单、收据、发票、催缴、押金、利润优势
吸收云门道的设备、通行、停车、能源、服务运营深度
不照搬会议、酒店/学校、健康码、平台财务、开发工具等非物业核心模块
```

这样菜单既完整，又不会被 33 个一级菜单拖散。
