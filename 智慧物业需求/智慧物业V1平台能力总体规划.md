# 智慧物业 V1 平台能力总体规划

> 目标：把物业系统中可跨场景复用的能力沉淀到平台，物业只保留业务策略和场景页面  
> 范围：平台基础、平台业务能力、物业场景、IOT/停车独立系统  
> 原则：平台提供框架，场景提供策略；不做“为平台化而平台化”
>
> 多场景扩展见：[智慧物业V1多场景扩展设计建议](智慧物业V1多场景扩展设计建议.md)

---

## 1. 总体结论

智慧物业中适合升级为平台能力的内容，分为四层：

```text
L0 平台基础能力
L1 平台业务能力
L2 物业场景能力
L3 独立系统
```

```text
L0 平台基础
  租户、组织、项目、地址、权限、数据范围、人员、空间、资产、设备资产、
  文件、消息、字典、区划、日志、统一查询、导入导出

L1 平台业务能力
  审批/工作流、合同生命周期、计费/收费内核、优惠/补贴引擎、
  供应商主数据、人员组/标签、PDF/文档模板

L2 物业场景
  物业费计价、能耗费公摊、车位管理费、业主关系、物业服务合同条款、
  物业收费项目、物业报表、公告/投票/装修/搬家

L3 独立系统
  IOT 设备平台、智慧停车、智慧消防、智慧安防、巡更、保洁
```

平台不能依赖 `prop_*` 表；物业可以依赖平台。

## 3. 重点平台能力设计

## 3.1 空间结构模板 + 资产类型

### 定位

平台资产基础配置，不是物业专属。

```text
bp_asset_space_template
bp_asset_type
```

### 模板

```text
tenant_id
scene_code        PROPERTY / GUARANTEE / PARK / CAMPUS
template_code
template_name
level_count
levels_json
version_no
status
```

规则：

```text
租户级模板库
不同场景用 scene_code 隔离
项目组织选择模板
模板版本化
已生成空间不自动重构
```

### 资产类型

```text
tenant_id
scene_code
type_code
type_name
type_category
```

物业类型示例：

```text
高层住宅、多层住宅、排屋、商业、商铺、办公、仓库
车库车位、露天车位、地下车位、充电车位
```

### 项目选择

```text
bp_iam_org.space_template_id
bp_iam_org.default_asset_type_code
```

### 场景扩展

```text
物业：prop_unit_ext.asset_type_code
保障房：保障房房屋扩展
园区/校园：各自扩展
```

## 3.2 设备业务资产能力

### 平台只做“设备作为资产”

```text
设备台账
设备编号/资产编号
设备类型/型号/厂商
所属项目/空间
安装位置/时间
责任人/管理人/维保人
质保期
采购/供应商/合同
业务状态
空间绑定履历
维修/更换履历
设备组
二维码
```

### 平台不做

```text
设备协议/通信
在线心跳/电量/信号
远程控制
设备告警
门禁/车闸/梯控
卡片/人脸/指纹
```

### 表设计

```text
bp_dev_device          设备资产主表，复用现有表
bp_dev_bind_log        设备空间绑定履历
bp_dev_group           业务设备组
bp_device_type         设备类型字典
bp_dev_service_record  设备运维履历
```

### 数据源

```text
IOT：设备身份、在线状态、运行状态
业务：资产属性、空间绑定、责任、质保、运维
通过 iot_device_id 关联
```

## 3.3 授权与人员钥匙包


```text

```

## 3.4 审批/工作流

### 为什么平台化

保障房、物业、园区都需要：

```text
合同变更
退租
换房
业主审核
优惠
退款
供应商签约
```

### 表设计

```text
bp_wf_flow
bp_wf_node
bp_wf_task
bp_wf_record
```

### 能力

```text
单级
多级串行
平级多人
会签 ALL
或签 ANY
金额分级
审批历史
统一待办
```

### 场景扩展

```text
场景提供：
  业务类型
  业务表单
  金额
  审批人角色
  节点名称
```

### 结论

```text
审核中心是物业页面
审批引擎是平台能力
不建 prop_audit_*
```

## 9. 风险与反模式

### 风险

```text
平台表反向依赖场景表
过度抽象导致大量 if/else
一次性重写保障房账单/合同
双写导致数据不一致
权限模型过粗
迁移影响现有业务
```

### 反模式

```text
把物业所有表改成 bp_ 前缀
为每个场景复制一套工作流
平台强依赖 prop_* 表
没有 scene_code/biz_type 的平台字典
没有版本的空间模板
没有审批历史的授权
```

---

## 10. 验收标准

平台能力应满足：

```text
至少两个场景可使用
不依赖场景专属表
租户隔离
项目数据范围
权限校验
操作审计
可配置扩展点
可渐进迁移
有回归测试
```

---

## 11. 最终建议

优先升级：

```text
1. 空间结构模板 + 资产类型（已完成）
2. 审批/工作流
3. 设备业务台账
4. 设备授权/人员钥匙包
5. 合同生命周期
6. 计费/收费内核
7. 优惠/补贴引擎
8. 供应商、人员组、文档、导入导出、查询、报表
```

不要升级：

```text
物业费计价规则
能耗费公摊
车位管理费规则
业主关系
物业服务合同条款
物业专属报表
IOT 控制
停车运营
```

总体原则：

```text
平台提供框架
场景提供策略
数据归属清晰
接口单向依赖
渐进迁移
```
