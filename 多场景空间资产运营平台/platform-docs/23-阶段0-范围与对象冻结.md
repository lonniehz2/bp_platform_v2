# 阶段 0：范围与对象冻结

> 项目：多场景空间资产运营平台  
> 阶段：0 / 6  
> 状态：设计冻结稿  
> 依据：总体设计基线 v1.1、保障房菜单结构设计、标准页面与模板阶段设计  
> 说明：本阶段不编码，只冻结范围、对象、边界和术语。

---

## 1. 阶段目标

在进入页面模板、状态矩阵、接口设计之前，先回答四个问题：

```text
这次设计到底覆盖什么？
不覆盖什么？
核心对象有哪些？
对象之间是什么关系？
```

如果这些问题不冻结，后续会出现：

```text
页面设计和数据模型对不上
接口按页面写，而不是按对象写
房源、可出租单元、合同、账单概念混用
保障房和市场化房源边界混乱
```

## 5. 术语冻结

| 术语 | 英文/编码 | 定义 |
|---|---|---|
| 租户 | Tenant | 平台隔离单位 |
| 组织 | Org | 租户内组织树 |
| 项目 | Project | 保障房/物业等业务项目，对应 `bp_org` |
| 空间 | Space | 楼栋、单元、楼层、房屋、床位 |
| 房源 | House | 可管理的物理房源资产 |
| 可出租单元 | RentableUnit | 整套、房间、床位等可独立出租单位 |
| 人员 | Person | 自然人主档 |
| 申请 | Application | 保障房资格申请 |
| 轮候 | Waitlist | 审核通过后的排队 |
| 配租 | Allocation | 轮候对象分配房源 |
| 合同 | Contract | 租赁合同 |
| 账单 | Bill | 应收费用 |
| 收款 | Payment | 实际收款 |
| 收据 | Receipt | 收款凭证 |
| 设备 | Device | IoT 设备或虚拟设备 |
| 绑定 | Binding | 设备与空间的唯一关系 |
| 授权 | Grant | 人员对空间的通行权限 |
| 事件 | Event | 设备上报事件或告警 |
| 审批 | Approval | 业务流程审批 |
| 房源配置 | Feature | 家电、家具、软装等配置 |
| 房源素材 | Media | 照片、视频、VR、户型图 |
| 房源发布 | Listing | 对外的房源商品信息 |
| 预约 | Booking | 看房预约 |
| 订单 | Order | 市场化房源交易订单 |
| 场景 | Scene | 保障房、物业、资产经营等 |
| 数据范围 | DataScope | 用户可见数据边界 |
| 审计日志 | AuditLog | 关键操作留痕 |

## 8. 对象生命周期概览

```text
申请：草稿 → 提交 → 审核 → 通过/驳回/退回 → 转轮候
轮候：等待 → 配租 → 已配租/取消
配租：待配租 → 已配租 → 已签约/取消
合同：草稿 → 审批 → 生效 → 变更/续签/退租 → 终止
账单：草稿 → 已出账 → 部分收款 → 已结清/逾期/减免
收款：收款 → 核销 → 收据；冲正/退款
设备：入库 → 绑定 → 使用 → 解绑 → 退役
审批：未提交 → 审批中 → 通过/驳回/撤回
房源发布：草稿 → 审核 → 已发布 → 下线/过期
订单：草稿 → 待支付 → 已支付 → 已签约/取消/退款
```

## 9. 边界冻结

### 9.1 平台与场景

```text
平台提供共享能力
场景提供专属流程和字段
场景不复制平台核心
场景不直接跨模块改表
```

### 9.2 保障房与市场化房源

```text
保障房：资格、轮候、配租，不线上下单
市场化房源：可展示、预约、下单
房源产品化模块服务市场化场景
保障房可使用展示和预约能力
```

### 9.3 内部数据与公开数据

```text
内部数据：成本、产权、业主、设备密钥、精确地址
公开数据：标题、描述、照片、面积、配置、价格、模糊位置
公开接口只返回审核通过数据
```

### 9.4 旧系统

```text
8080 保持原样
不迁移
不改造
不双写
不依赖
新系统验收通过后直接替代
```
