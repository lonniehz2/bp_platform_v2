# 设计原则：从意图到结果，不做字面功能

## 核心原则

任何修改或新增，不得只完成字面需求。必须先确认：

```text
用户真正想达到的结果是什么
这个结果在页面上如何被看到
数据如何被保存
后端/导出/打印是否同步
刷新/重新进入后是否仍然成立
失败和边界如何处理
```

如果意图不明确，先问清楚，不靠猜测实现。

## 完成定义

一个功能只有同时满足以下条件才算完成：

```text
1. 用户能看到变化
2. 变化可保存
3. 重新进入后仍然存在
4. 相关输出同步变化（PDF/导出/打印/报表）
5. 失败时有明确提示
6. 权限和数据范围正确
7. 有可执行的验证方式
```

## 反例

### 页面尺寸切换

只修改下拉框的值，不改变画布：

```text
错误：下拉框显示 A5，但画布仍然是 A4
```

只改变画布，不改变 PDF：

```text
错误：设计器是 A5，下载的 PDF 仍然是 A4
```

### 正确结果

```text
选择 A5
→ 设计画布变成 A5
→ 保存的 pageSize = A5
→ 重新进入仍然是 A5
→ PDF 预览是 A5
→ 正式收据 PDF 是 A5
```

## 执行流程

### 1. 先复述意图

在实现前用一句话确认：

```text
用户要的不是"一个下拉框"
而是"选择尺寸后，设计、预览、保存、输出都按新尺寸工作"
```

### 2. 找完整链路

```text
UI 控件
→ 前端状态
→ 模板 JSON
→ 保存接口
→ 后端渲染
→ PDF/导出
→ 重新加载
```

### 3. 定义验收结果

用用户能观察到的结果描述：

```text
切换 A5 后画布宽度从 595 变为 420
保存后重新进入仍是 A5
预览 PDF 页面尺寸是 A5
正式收据 PDF 页面尺寸是 A5
```

### 4. 不完整就停下来确认

如果只能完成链路的一部分，必须明确告诉用户：

```text
现在只完成了 UI，后端 PDF 还未同步
```

而不是把半成品说成完成。

## 适用场景

```text
页面尺寸
模板格式
印章位置
字段显示/隐藏
导出字段
权限控制
状态流转
多语言
场景切换
```

## 验证要求

每个功能至少验证：

```text
页面可见变化
保存后重新加载
后端接口/数据库
PDF/导出结果
异常路径
```

## 一句话

> 不要实现“用户说的按钮”，要实现“按钮背后用户真正想得到的结果”。
