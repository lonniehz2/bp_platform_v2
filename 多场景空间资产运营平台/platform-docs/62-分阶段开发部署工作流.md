# 分阶段开发、部署与验证工作流

> 目的：减少 VPN 依赖，把部署和验证集中到固定窗口  
> 原则：开发阶段不连服务器，部署阶段一次完成

---

## 1. 两个阶段

### 阶段 A：开发阶段（VPN 断开）

```text
需求确认
编码
前端 build
后端编译
静态检查
单元测试
提交 Git
整理部署清单
```

不做：

```text
不连 192.168.31.11
不执行远程 SQL
不部署
不反复试探服务器
```

### 阶段 B：部署验证阶段（VPN 连接）

```text
检查 VPN 和服务器
备份数据库/旧 jar
执行 SQL 迁移
上传 jar
重启服务
健康检查
核心断言
权限检查
页面烟测
记录结果
```

只有这个阶段需要 VPN。

---

## 2. 批量节奏

建议每批包含：

```text
1 个完整功能
或 3~5 个相关提交
或 1 个数据库迁移
```

不要每改一个按钮就部署一次。

每批开始前生成：

```text
批次清单
  改动文件
  数据库变更
  需要验证的页面
  回滚方式
```

---

## 3. 开发阶段交付物

```text
Git 提交
前端 build 结果
后端编译结果
待执行 SQL 文件
验证清单
```

如果前端依赖数据库迁移：

```text
标记“必须与 SQL 同一批部署”
不允许单独部署前端
```

例如菜单编码统一：

```text
SQL 018_menu_unify.sql
navConfig 页面编码
PermissionInterceptor 权限映射
三者必须同一批
```

---

## 4. 部署阶段顺序

```text
1. 确认 VPN 已连接
2. 检查 8090 健康
3. 备份数据库和旧 jar
4. 执行 SQL 迁移
5. 校验数据库结果
6. 上传最新 jar
7. 重启服务
8. 等待 health 200
9. 跑 verify-core
10. 跑 verify-deploy
11. 跑 verify-permissions
12. 页面烟测
13. 记录批次结果
```

---

## 5. 失败处理

```text
上传失败：断点续传或重试
健康失败：回滚 jar
SQL 失败：回滚事务/备份
断言失败：停止后续页面验证
VPN 断开：暂停，不反复重试
```

不把“部署失败”留在后台反复重试，避免网络和时间浪费。

---

## 6. 交互约定

你可以直接说：

```text
进入开发阶段
```

我会：

```text
断开服务器依赖
只编码、构建、提交
整理部署清单
```

部署时你说：

```text
进入部署阶段
```

我会：

```text
连接服务器
一次完成本批部署和验证
给出结果
```

如果 VPN 未连接：

```text
只做开发阶段
不尝试远程部署
```

---

## 7. 当前建议的下一批

```text
批次：用户与权限页面完整化
内容：
  角色默认数据范围
  用户例外收窄
  最终权限预览
  角色页去掉场景菜单
  左侧栏后端菜单驱动
```

其中：

```text
菜单编码统一 SQL 已执行
左侧栏页面编码已改
角色页功能权限已改为页面级
```

下一批可以专注：

```text
角色数据范围
用户范围例外
最终权限预览
```

---

## 8. 结论

```text
开发阶段：VPN 断开，专注代码
部署阶段：VPN 连接，一次部署验证
批次交付：清单化、可回滚
```

这样能把 VPN 占用时间压到最低，也避免半成品部署到线上。
