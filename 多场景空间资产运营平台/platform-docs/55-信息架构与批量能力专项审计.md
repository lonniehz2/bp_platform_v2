# 信息架构与批量能力专项审计

> 审计视角：按“申请/合同/收款”同类问题重新检查全系统  
> 范围：54 个页面、48 个业务路由  
> 结论：同类问题不止 3 个页面，主要集中在“主数据页”和“多实体工作台”

---

## 1. 判定标准

本次不再按“页面有没有 bug”检查，而按四个问题检查：

```text
A. 是否把多个独立任务堆在一页上下滚动
B. 是否列表和详情混在一起
C. 是否只有单条新增、没有批量导入
D. 是否用平铺下拉代替层级/空间选择
```

判定原则：

```text
同一实体的不同侧面 → 详情页 Tab
父子关系强 → 主从布局
独立业务 → 拆路由
低频编辑 → 抽屉
高频操作 → 列表行操作
批量录入 → 导入向导
```

---

## 2. 总体结果

```text
54 个页面中
3 个以上 panel 的页面：15 个
5 个 panel 的页面：1 个（Contracts）
4 个 panel 的页面：6 个

批量导入：仅设备 1 个
批量导出：仅报表/监管报送 2 个
DataTable：6 个页面
其余大量列表仍是手写 table，无统一搜索/分页
```

结论：

```text
“申请/合同/收款”的问题不是孤例
人员、设备、项目、房源展示、押金、用户、菜单都有同类结构
```

## 4. 批量导入缺口

当前只有：

```text
设备导入（DeviceBinding 页面内，CSV）
```

缺口：

| 实体 | 现状 | 优先级 |
|---|---|---|
| 人员 | 只能单条新增 | P0 |
| 房屋/空间 | 只能单条新增 | P0 |
| 设备 | 有 CSV，但入口在设备绑定页 | P0 |
| 用户 | 只能单条新增 | P0 |
| 合同 | 只能单条新建 | P1 |
| 计费项目 | 只能单条新增 | P1 |
| 表计 | 只能单条新增 | P1 |
| 房源展示 | 只能单条新增 | P2 |
| 补贴 | 只能单条新增 | P2 |
| 工单/预警/投诉 | 通常不需要导入 | 低 |

### 建议的统一导入模型

```text
列表工具栏：批量导入 / 下载模板 / 导入记录
抽屉三步：
  1. 下载模板
  2. 上传并校验
  3. 确认导入 + 下载错误行
```

后端建议：

```text
GET  /imports/{entity}/template
POST /imports/{entity}/validate
POST /imports/{entity}/commit
GET  /imports/{entity}/jobs/{jobId}
```

规则：

```text
必填列和字典列写进模板
逐行校验
允许部分成功
错误行返回行号和原因
全部失败不落库
导入写审计
大文件异步
```

不建议每个页面各写一套 CSV 解析。

## 7. 设备绑定专项

当前：

```text
未绑定设备下拉
绑定空间下拉
绑定按钮
已绑定列表
```

问题：

```text
空间层级丢失
看不到某空间绑了哪些设备
直接绑定和继承绑定混在一起
批量绑定困难
```

建议：

```text
左侧空间树
右侧当前空间设备
  直接绑定
  继承设备
下方未绑定设备托盘
支持多选批量绑定
支持行内解绑
支持扫码/编码搜索
```

不建议继续用两个下拉框承载空间关系。

## 10. 改造优先级

### P0

```text

人员/设备/项目拆列表 + 详情

押金/补贴并入合同详情

```

### P2

```text
列表统一 DataTable

导出

```

## 11. 结论

```text
同类问题不是只有申请/合同/收款
人员、设备、项目、房源展示、押金、用户、菜单都存在“多任务一页”
批量导入几乎空白
设备绑定仍是最不直观的空间操作
```

建议先做三件事：

```text
1. 申请/合同/收款信息架构重构
2. 统一批量导入框架，先做人员/房屋/设备
3. 设备绑定空间树主从改造
```

其余页面按 P1/P2 逐步收口。
