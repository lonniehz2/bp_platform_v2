## 2. 新增规则：空间授权向上继承

这条规则必须先进入模型，否则 IoT 同步会算错权限。

### 规则定义

```text
空间授权不允许向下继承
子空间授权默认包含父空间访问
```

即：

```text
授权 A栋/1单元/101
  → 可以进 101
  → 必须能进 A栋/1单元门禁
  → 必须能进 A栋门禁

授权 A栋/1单元
  → 可以进 1单元门禁
  → 不能进 101

授权 A栋
  → 可以进 A栋门禁
  → 不能进 1单元
  → 不能进 101
```

### 生效范围公式

```text
effectiveSpaces(grant at S) = {S} ∪ ancestors(S)
```

不是：

```text
{S} ∪ descendants(S)
```

### 影响

```text
授权计算
设备绑定
门禁设备选择
IoT 下发
访客授权
临时人员授权
权限展示
```

### 必须确认

```text
1. 子空间授权是否自动包含所有祖先空间的“通行类设备”？
   建议：是。

2. 父空间授权是否完全不包含子空间？
   建议：是。

3. 兄弟空间是否互相不影响？
   建议：是。

4. 设备级授权是否也需要祖先空间通行？
   例如只授权 101 的门锁，但没有 1单元门禁权限，实际进不去。
   建议：设备授权单独确认是否需要附带祖先通行。
```

### 实现归属

需要先定：

```text
A. 业务系统计算祖先闭包，向 IoT 下发有效设备范围
B. IoT 根据空间树自己计算祖先闭包
```

建议：

```text
IoT 有空间树时，由 IoT 统一计算
业务系统只下发授权空间和规则
避免两边算法不一致
```

---

### 设备类型与设备授权（单独规则）

设备类型由设备管理员在入库时选择，功能由类型决定。

功能分类：

```text
PASSAGE        小区门、楼栋门、单元门、梯控、闸机
ENTRY_LOCK     入户门锁
INDOOR_LOCK    室内门锁
METER          表计
SENSOR         传感器
OTHER          其他
```

通行类：

```text
PASSAGE / ENTRY_LOCK / INDOOR_LOCK
```

非通行类：

```text
METER / SENSOR / OTHER
```

规则：

```text
非通行类设备跟随空间授权，不做单独权限控制
设备级授权只用于通行类设备
```

空间授权：

```text
accessDevices(S) =
  devicesAtSpace(S)
  ∪ ancestorPassage(S)
```

设备授权：

```text
accessDevices(D at S) =
  {D}
  ∪ ancestorPassage(S)
```

示例：

```text
授权 101 入户门锁
  → 101 门锁
  → 1单元门禁
  → A栋门禁
  → 不可开 102 门锁

授权 101 空间
  → 101 门锁、表计、传感器
  → 1单元门禁
  → A栋门禁
```

“实际生效范围”是计算后的只读结果，在设备详情展示。

## 11. 不建议现在做

```text
车位模型
复杂审批流
移动端全面适配
大数据量优化
```

这些应放在 IoT 授权和主数据闭环之后。

---

## 12. 结论

```text
IoT 同步前最重要的工作不是写同步接口
而是先确认空间授权向上继承规则
并停止业务侧四级授权双写

业务闭环仍有一批编辑/终止/归档缺口
信息架构仍有申请/合同/收款三页堆叠
批量导入只有设备
设备绑定仍不直观
```

建议先做：

```text
1. 空间授权向上继承规则
2. IoT 接口与映射
3. 旧授权停写
4. 数据体检
5. 再进入设备授权策略开发
```
